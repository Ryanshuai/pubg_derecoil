# control/ — 驱动层

驱动游戏。每个动作都是 **observe → act → verify** 的闭环：读屏幕拿当前状态，发动作，再读回来确认落地了。

**发出去的动作不算数，读回来的才算。** 这是这一层唯一的铁律，下面所有东西都是它的推论。

## 等级：调用之前先问「我要多强的保证」

```
pixi run surface            11 个意图，每个的 L2/L1/L0/R
pixi run surface kit        看某一个
pixi run surface-check      三条机器判据，见下
```

| | 返回真意味着 |
|---|---|
| **L2** | **目标已达成**，屏幕确认过，内部会重试。从这里开始，正常情况不该需要别的 |
| **L1** | **这一步落地了**。目标由调用方编排和重试 |
| **L0** | **机制层**：守卫在上一层，直接调等于绕过去 |
| **R** | 不驱动游戏：读一个答案，或只记一笔 |

⚠ **等级是保证的强度，不是调用的粒度。** 这条踩过三次：`home_to_clamp` 是一次很大的移动、**零验证**，按大小归会高一级；`drag` / `right_click_equip` 全都读回并重试，所以「L0 = 没验证」是假的——它们真正的问题是**验错了对象**（`right_click_unequip` 验的是「槽空了」，而枪掉在地上时槽也是空的）。

### 三条机器判据（`pixi run surface-check`）

1. **R 不许驱动。** 语法可判，且是**传递**的——`recenter` 隔一个私有跳就摸到硬件。
2. **每个 L0 必须点名守卫**，机器验那个守卫存在、等级更高、而且**现在还在调它**。
   「守卫在上一层」这句话写了一年，第一次跑就发现 **12 个 L0 里有 5 个在 `control/` 里根本没有守卫**——`ads_tap` 的守卫在 `capture_ads.py`，`arm`/`disarm` 的在 `sweep.Rig.arm`，`auto_equip` 的守卫存在但**没归类所以看不出它是守卫**。而我第一批写下的守卫名字**有两个是猜的、两个都错**，机器当场说了。
   跨层守卫不一定是错的（`--no-comp` 确实是实验的决定），但**必须可见**——以前它只是一句 docstring。
3. **docstring 的第一行标签必须等于表里的等级。** 两处各自被不同动机改动：修函数的人改前者，审接口的人改后者。第一次跑抓到两笔——`disarm` 上午修好升了 L1、表里还是 L0；`hold` 在文件里降成 L0、表里还是 L1。

### 一个逃生口，而且它自己被验着

`InventoryControl` 的**每一次读都会挪光标**（`park()` → PARK_XY），因为悬停的槽位会给自己画 tooltip 而槽位读是模板匹配。所以 12 个「读」在语法上全是驱动。

它们归 R，靠 `CURSOR_ONLY`——但这个口子**不自证**：`_cursor_only()` 会把 `park()` 掏空再跑一遍真正的分类器，只有当那个 ref **不再驱动**才放行，同时验 `park` 自己除了 `move_to`/`cursor_pos` 没碰别的。给 `park` 加一次点击，12 条 R 同一轮全红（验过）。

这个文件的前两个逃生口都是散文判据（「docstring 里有 ⚠」「提到 `<param>=True`」），**两个都放行了它们本该拦的那个东西**。

## 先决条件：焦点，每次都要

**驱动任何东西之前先 `ensure_focus()`。** 游戏不在前台时驱动鼠标，等于往当前前台的窗口里乱点乱打。

```python
from control.focus import ensure_focus, focus_keeper

if not ensure_focus(countdown_s=6):    # 抢→验→重试3次→倒计时兜底→settle
    return 1
...
if not focus_keeper().ok('mag 3'):     # 跑到一半掉了就抢回来，上限 5 次
    break
```

三个坑：

- **裸 `SetForegroundWindow` 会被拒。** Windows 只允许当前前台进程交出焦点。`raise_game()` 用 `AttachThreadInput` 借前台线程的输入队列绕过去；不模拟 ALT 键，因为 ALT 在这游戏里是自由视角。
- **调完必须再验一次 `game_focused()`。** 它可以不报错地失败——曾经有个 run 第一行打印 `focused=True`，然后打不开刷新器面板。
- **焦点不是拿到一次就固定的。** 终端会反复抢回去。**关键操作要每次重试前重新抢**，别只在开头抢一次。
- **切前台后头几帧游戏不收输入**，所以 `ensure_focus()` 成功抢到之后自己会等 `FOCUS_SETTLE_S`（0.6 s），调用方不用再 sleep。已经在前台时**不等**——没有前台切换就没有被吞的帧。这个等待原来散在 25 个调用点里，漂成 0.4/0.5/0.6/0.7/0.8 五个值，没有一个有实测支持。要自己管就传 `settle_s=0`。

**最小化不用管，`raise_game()` 自己会还原。** 刷 Pico 固件会把游戏丢回桌面——但游戏没退，只是最小化了，就是任务栏那个头盔图标。`raise_game()` 里 `IsIconic` → `SW_RESTORE` 干的正是点那个图标的事，实测 `minimised=True focused=False` → `minimised=False focused=True`（2026-08-03）。所以刷完固件直接 `ensure_focus()` 就行，不需要人点。

**分得开的两种情况**，别猜：

| `game_hwnd()` | 意思 | 怎么办 |
|---|---|---|
| 返回 hwnd，`IsIconic` 为真 | 最小化，进程活着，**但截屏读到的是桌面** | `raise_game()`，够了。判据用 `game_minimized()`，别自己 `IsWindowVisible`——它对最小化窗口返回真 |
| 返回 `None`，`game_pids()` 非空 | 正在起 / 正在退 | 等，别拉第二个 |
| 返回 `None`，`game_pids()` 空 | 进程真没了 | 抢焦点帮不上，`LobbyControl.ensure_running()` |

窗口回来之后游戏在哪个界面是另一回事——刷完固件常常掉回大厅，接着走 `LobbyControl.ensure_in_match()`。

窗口有焦点 ≠ 游戏在收输入：标题匹配在大厅、加载页、结算页全都成立。焦点之外还要过 `LobbyControl` 那关。

## `ensure_weapon_in_hand` 拒绝的两件事（2026-08-08）

它一直在**读架子**再决定刷不刷（`[stock] m416 already in slot 1` 就是它）。加的是两条**拒绝**：

| 情况 | 以前 | 现在 |
|---|---|---|
| `loadout()` 返回 None | `ac.loadout()['guns']` → **TypeError**，四层之下抛「'NoneType' object is not subscriptable」 | 拒绝并说清楚 |
| 架上**两把同名枪** | 照常 `hold` 第一把 | 拒绝 |

**「架子是空的」和「我看不见架子」从这里看一模一样，而其中一个的结局是货架上多一把枪。**

⚠ **两把同名枪是下游谁都描述不了的状态。** 实测：架上两把 mp5k，标定读了一把的配件、打了另一把，一梭装满配件的枪进了 `bare` 格。**它在每一个印出来的数里都是隐形的**——40 发打满、fps 正常、那一格 5 梭互相一致。唯一的破绽是总量：428 counts 对 905，也就是 0.473，正好是这把枪 comp+vert+heavy 的实测因子。

这是根 `CLAUDE.md` 第二条法则在这一层的实例：**读回描述的对象，不是开火的那个对象。**

## 状态：两种，别混

**屏幕瞬时状态**（大厅在不在结算画面、刷新器哪列展开了）——**现测，永不缓存**。

`LobbyControl.state()` 直接透传 `det.state()`，`SpawnerControl.sync()` 每次重读。这是对的，别改成缓存。危险写法是 `self._expanded = True`（我点过所以它是开的）——游戏会掉线、会弹窗、会被另一个 agent 抢走，缓存必然骗你。

**游戏世界状态**（当前枪、配件、火力模式）——在 `detector/game_state.py`，不在这一层。因为它不是每帧可观测，且 `robot` 和多个 control 要读同一份。**写入由观测驱动，不由「我发过这个动作」驱动。**

最后那句是 2026-08-02 补上的，因为 `state.tab_open` 违反了它整整一年：按 Tab 就把缓存布尔量取反（`toggle_tab_open`），300 ms 后再读屏幕纠正。那 300 ms 里它是猜的，而十几条 `cond: '!tab_open'` 拿它当闸门——包括压枪开不开。**按键被吞**（见 `docs/game_quirks.md`）就会让它反过来且无人察觉。现在归 `TabWatch` 管，只有看过屏幕才动。离线回归 `pixi run tab-watch`；实机对照跑过 20/20 与屏幕一致（那个探针 2026-08-08 删了，它就是十几行「开关 Tab、每次读屏对一次」）。

## 用法

### 确保在局内

```python
from control.lobby import LobbyControl
with LobbyControl() as lc:
    if not lc.ensure_in_match()['ok']:
        return                # 大厅/加载/结算/菜单，任意态都会自己走到局内
```

测量值和状态机全在 `calibration/artifacts/lobby/README.md`。两个坑：

- **ESC 菜单的像素探针全都说「在局内」**。不查 `SYSTEM MENU` 标题就会返回 `playable=True`，而按键全被菜单吃掉。
- **别用固定 `sleep` 等游戏。** 结算页 ~18 秒、匹配+加载不是常数。`EXIT_TIMEOUT`/`ENTER_TIMEOUT` 是放弃阈值，不是预期耗时。

### 开关游戏 —— **进程是同一根轴上的第一个状态**，不是另一件事

```python
lc.ensure_running()                  # 没进程就通过 Steam 拉起来，等到有屏幕可读
lc.quit_game()                       # 终止进程（不点 EXIT TO DESKTOP，见下）
lc.restart_game()                    # 卡死了用这个：quit + launch
lc.ensure_in_match(launch=True)      # 无人值守要的那条，默认关
```

CLI：`python control/lobby.py launch|quit|restart`，这三个**跑在焦点闸之前**——它们正是「没有窗口可抢焦点」时才被调用的。

**为什么必须先问进程再问屏幕**：游戏关着的时候桌面是亮的，`bar_max` 读 **251**、`ping_frac` **0.000**，`classify()` 给出 `FULLBLEED`——而三条策略都把 FULLBLEED 当加载页处理，**什么都不点，等**。于是一个死掉的游戏要烧满 300 秒 `ENTER_TIMEOUT`，然后报告说游戏慢。**一个不会说「这里什么都没有」的探针，必须由一个会说的挡在前面。**

三个态分得很开，因为**恢复动作两两不同**——这就是它们是三个状态而不是一个「屏幕读不了」的全部理由：

| | 判据 | 怎么办 |
|---|---|---|
| `NOT_RUNNING` | 没有 tslgame 进程 | 发 Steam URL，分钟级 |
| `NO_WINDOW` | 有进程，`game_hwnd()` 是 None | **等**。正在起或正在退，再发一次 URL 只会弹出 Steam 自己的「已在运行」框——那个框本仓库看不见也点不掉 |
| `MINIMIZED` | 有窗口，`IsIconic` 为真 | `raise_game()`，**实测 1.4 秒**一个动作就好 |

⚠ **`MINIMIZED` 是同一课往前一格，而且先花了 420 秒才有人看。** `IsWindowVisible` 对最小化的窗口**返回真**，所以 `game_hwnd()` 交回一个谁都截不了的窗口，抓回来的是桌面：`bar_max=251` / `ping_frac=0.000` → `FULLBLEED` → 「加载中，等着」。那一版的 `LAUNCH_TIMEOUT` 整个烧完，而游戏一直是可驱动的。**「先问进程再问屏幕」是对的，只是少问了一个问题。**

⚠ **判据放在 `state()` 里，不在某一条策略的 `act()` 里。** 它第一次是修在 `ensure_running` 里的——另外三条策略和 `state()` 自己仍然把桌面报成加载页。**一个「已经修好」的东西和一个没修的，从外面看一模一样**（`detector/CLAUDE.md` 的 `_nudge_backdrop` 是同一个形状）。

⚠ **`state()` 只报告，不还原。** `raise_game()` 抢前台，而一个读函数去挪它被要求描述的那个窗口，正是本文件「屏幕瞬时状态现测、永不缓存」那条禁的东西。还原是四条 `act()` 里的 `restore_window()` 干的。

⚠ 便宜的问题先问：`game_hwnd()` **1.4 ms**，`game_pids()` **18.7 ms**（603 个进程，2026-08-07 实测）。所以只有窗口答 None 才去翻进程表。

⚠ **`quit_game()` 终止进程，不点 EXIT TO DESKTOP，这是故意的。** 最需要关掉游戏的那些画面，恰恰是菜单不管用的画面：卡死的加载页、Steam 自己的模态框、本仓库读不出来的 ESC 菜单。**只在游戏健康时才管用的退出不叫恢复。** 另一半理由是 `EXIT TO DESKTOP` 是**两个菜单上都有**的唯一一项（局内 y=634、大厅 y=949），盲点坐标打偏的后果正好就是「退出游戏」——在这里它是目的，也就是唯一一个点错了不会有人发现的地方。先 `terminate()`，`QUIT_GRACE` 10 秒还在就 `kill()`。

⚠ **`ensure_running()` 不保证到大厅，也不保证焦点。** 它的目标是 `SETTLED`（游戏起来了、画着一个叫得出名字的屏幕），可能落在 `DISCONNECTED` 或一个陈年 `ERROR` 框上——清它们是 `ensure_in_match` 的活，它本来就会。焦点自己 `ensure_focus()`，冷启动大半时间根本没有窗口可抢。

⚠ **`LAUNCH_TIMEOUT = 420` 是这个文件里唯一没有实测支撑的上限。** 跑一次把真值填进 `OBSERVED DURATIONS`。

### 大厅的 ESC 菜单曾经**整个是隐形的**（2026-08-07 修）

在大厅按 Esc 弹出的是**同一个菜单，低 315 px**：标题、字形、x、85.3 px 行距全都一样，只有第四项从 `LEAVE TRAINING` 变成 `RESTART LOBBY`。而**大厅带不带菜单都是 letterbox**，所以 `bar_max` 照读 0，整帧判成 `LOBBY`——然后 `press_play()` 把 PLAY 点进一个吞掉它的模态框，每 15 秒一次，直到 300 秒上限。

**跟 `ERROR` / `RECONNECT` 是同一个形状**（压在大厅之上、状态照读 LOBBY、吞掉那唯一一次点击），所以修法也一样：给它一个自己的状态 `LOBBY_MENU`，三条策略都按 ESC 关掉它。

⚠ **一个模板，两个搜索窗口**，因为答案不同：局内的菜单关掉是为了继续打，大厅的菜单关掉是为了够到 PLAY。两侧都量了（`pixi run lobby-detector`，9 例）——各自在自己的位置 **0.999**，在对方的位置 **≤0.075**，闸门 0.55。

### 进局之后挪到 200m 射击场 —— **它是「进局」的一部分，不是一条清单项**

**不用自己调。`LobbyControl.ensure_in_match()` 自己在做**（`range_name='200m'`，传 `None` 关掉）。要单独驱动地图才用 `control/map.py`：

```python
from control.map import MapControl
with MapControl() as mc:
    mc.goto_range('200m')      # M → 点黄框 → M，落地靠读回玩家标记
```

出生点是主场地，人多的服上有人开车从中间穿过。**被撞掉的弹匣不会自己报告**——后坐力轨迹里只是混进了别人的物理，而下游每一道闸照样绿。

四条：

- **落地判据是读回玩家标记落到 spawn 点，不是点击返回。** 点歪了和游戏没接，留下的屏幕**一模一样**。判据能成立的原因见 `detector/CLAUDE.md` 的「大地图 + 传送点」。
- **幂等**：开图后先看在不在，已经在了就只付一次开关图，不点。
- ⚠ **关地图是 `finally`，不是每个 return 前一行。** 上一版是后者，于是**抛异常那条路完全没覆盖**。地图开着交还给调用方的话，后面每一次按键和点击都进地图而不进游戏，**下游没有任何东西会去测这件事**。唯一不关的是「图压根没开起来」那一支——那时按 M 是**打开**它。
- ⚠ **M 是 toggle，所以重发一次不需要的 M 会撤销这一步。** 这跟 `ensure_tab` / `ensure_panel` 是同一课，`ensure_map` 因此**先读后按**。真正结束一个卡住的步骤的是 `MAP_MAX_RETRIES`（4×1.5s ≈ 6s），不是 `MAP_TIMEOUT`——直接抄 lobby 的 `MAX_RETRIES=3` 会变成「4.5 秒放弃」而注释还写着 15 秒上限。

⚠ **`MAP_SETTLE` 没实测**，其余三个常量有一次实机数据（每步都是第一次尝试就成，2.3s 冷 / 1.4s 已在）。

#### 它搬过两次家，两次的理由都值得留着

| 住在哪 | 为什么搬走 |
|---|---|
| `LobbyControl` 里（最早） | M 是按键，**Tab 和刷新器面板都吞按键**，而查这两样的 `session.ensure_ready()` 是 `lobby` 的**消费者**——从里面够不着。那一版只验 `IN_GAME`，Tab 开着跑它会报「按键没生效」，真相是有块屏幕在吃键 |
| `session.ensure_ready()` 的第五条腿 | 它靠一个「这个进程已经走到靶道了」的标志跳过重复传送，**而那个标志放错了模块**：见下 |
| **`LobbyControl.ensure_in_match()`**（现在） | 移动角色的那个模块，就是知道角色被移动过的那个模块 |

**中间那一版是怎么坏的，以及为什么第一版的理由现在不成立了。**

`ensure_ready` 不是回到局内的唯一一扇门，而那条腿的整个正确性建立在「是」上面。另外两扇：`AutoSession.enter()` 直接走 `LobbyControl`，人自己 alt-tab 回去再进一局。两条都不会清那个标志，于是下一次 `ensure_ready` **跳过了一次从未发生的传送**——一轮 17 分钟被踢出去的 harvest，回来站在出生主场地，**后半程 45 分钟全在车流里打完**，每一道闸绿着。当时的修法是加一个公开的 `forget_range()` 让这些调用方记得调，**那是同一个 bug 前面加了一个手动步骤**。

而第一版那条「Tab 和面板会吞 M」现在不适用，理由是**关于游戏的事实，不是一个顺序承诺**：`_place_on_range` 只在 `ensure_in_match` **自己刚走进来**那条路上无条件传送，而一局刚**加载完**的比赛不可能有模态屏幕开着——不是「我们把它关了」，是**它们开不出来**。

⚠ 另一条路（「本来就在局内，但这个进程还没放过人」）确实可能有 Tab 开着，**那里不检查**。失败是响的（`goto_range` 报「N 次尝试没生效」）、记在 `rec['range']` 里交给调用方，而替代方案是在 `lobby.py` 里 import `InventoryControl` 和 `SpawnerControl`，去问两个调用方紧接着就要问的问题。

**判据现在是 `rec['states'][0] != 'in_game'`**——`_pump` 把经过的每个状态都记下来，第一个就是它进门时看到的那个，所以这句话恰好是「这次调用是走进来的」，也恰好是「人在出生点」。**不要换成 `actions > 0`**：那是同一件事的弱写法，在「本来就在局内、只是清了个模态框」那条路上答错。

剩下那个 `forget_placement()` **只有一个调用方，而且必须保持只有一个**：`ManualSession.enter()`，它站在那里等一个**人**回到局内——这是本进程唯一观测不到的搬运工。

### 刷东西 — 三层，按需要进入

**要一堆东西，用 L2 批量入口**（绝大多数情况用这个）：

```python
from control.spawner import SpawnerControl
with SpawnerControl() as sc:
    sc.give_many(['m416', 'comp_ar', 'vert_grip', 'red_dot', 'backpack3'])
```

`give_many` 先 `plan()`：**gear 排最前**（它盲驱动，需要全折叠态），其余按类别聚合，面板每个类别只开一次、末尾统一收一次。9 件东西跨 5 个类别，类别点击从 ~18 次降到 ~6 次。

**想先看它要干什么**（不碰游戏）：

```python
for s in sc.plan(keys):
    print(s['kind'], s['key'], s['category'], s['index'], s['times'])
```

**要自己控节奏，用 L1**：

```python
sc.sync(need_cols=(1, 2))
st = sc.read()                     # PanelState，一帧读出，不需要基线
print(st)                          # <panel open, col2_row03 expanded, 7 entries>
rec = sc.goto(2, 3)                # 最短路径到这个节点
sc.click_entry(rec['entries'][4])  # 直接点第 5 项
sc.collapse_all()                  # 回根（现在是可选的，不是每次必须）
```

`read()` 是**绝对**的：一次截图读出「面板开着吗 / 哪个类别展开着 / 有哪些子项」，不跟任何基线比，所以序列中间读和开头读一样可信。原理和 42 帧真值验证见 `calibration/artifacts/spawner/README.md` 第 3b 节，回归测试是 `pixi run panel-state`（离线）。

**要手动救场，用 L0**：`click_category(col, row)` / `click_entry(entry)` 只发点击，不读不验。

三个坑：

- **驱动路径上一个识别都没有，这是铁的。**（2026-08-04 改完）类别行的 y 是常量表，条目坐标是 `entry_point()` 算的（`cat_y + 44.25 + k*50.70`，x = 列左 +237），展开验证是**帧差**——点击前后数列内改变了多少像素。全程只有一次识别：三个按钮图标那道「面板开着吗」，而它是唯一背景无关的（图标不是文字，24 正样本 0.989–1.000 对 0 负样本）。

  **为什么必须这样**：面板 = `blur(bg)*0.49`，对着天空时 `read()` 会在全折叠的面板上报 `col1_row02 expanded, 2 entries`——不是报错，是格式完全正确的假答案。一整轮采集（12 轮死 8 轮）就这么没的。细节和 A/B 数字在 `detector/CLAUDE.md`。

  常量在 `spawner_layout`，拿 `calibration/artifacts/spawner/runs/` 全部 42 张展开图验过：三列每个类别每条目吻合到 **3.1 px** 以内。**验收是对着天空刷东西**，`give_many` 3/3。
- `sync()` 只回答「面板在不在屏幕上」，坐标一个都不读（它自己的注释里写着）。要重新量坐标是 `sync(recalibrate=True)`，那是 `tools/scrape_spawner.py` 的事。
- **类别行的 y 不随展开变化**（实测 42/42 帧）——展开只把**下面**的行推下去。所以同一个点既能开也能关它，`_spawn` 因此总是关掉自己开的那个，`plan()` 也把同列的类别按**自底向上**排序。这条不变量成立，常量表就永远有效。
- ⚠ **展开态下 `find_menu` 会在 3~14 行之间乱跳**（子菜单的居中行混进行检测）。它现在是兜底，不是主路。
- 刷出规则（空栏进 1 格 / 满栏顶掉的枪掉地上 / 配件进背包）见 `docs/game_quirks.md`。

### 「读不出」不是「没装上」——面板是半透明的，换个背景再读

**读回有三种答案，不是两种**：读出这个件、读出**别的**件、**读不出**。第三种以前被当成第二种处理，代价是 2026-08-05 全因子里的 **11 格**。

`kit_faults` 对 `AMBIGUOUS` 的注释原来写着「a retry cannot improve a reading」。**重拖**确实不能，**重读**可以——Tab 面板半透明，槽位图标是合成在世界之上的，背景一暗，相邻件的余量就塌：

| 同一把 vector，同一个弹匣槽，转一下视角 | 最佳 | MSE | margin |
|---|---|---|---|
| 暗背景 | `quick_smg` ✗ | 267.7 | **1.02** |
| 另外六个视角 | `ext_smg` ✓ | 88–164 | **1.67–2.74** |

**件一直好好地装在枪上**，而 `ensure_kit` 把「读不出」判成「没落位」，重试、失败、废掉整格。现在歧义时**轻推视角再读**（`AMBIGUOUS_REREADS`，有界两次，歧义一消就停）——和 `GunDriver.ensure_posture` 读不出姿势图标时用的是同一招，理由也一样：**动图标背后的东西，再问一次**。

⚠ 只重读 `verifiable: False` 的。**槽位读出了另一个件的名字是真分歧**，重读说不出新东西。

### 读出的是**旧件**时，是游戏拒绝还是本项目的 bug —— 只有同场对照分得开

「读出了另一个件」里有一个特殊子类：读出的正是**装之前就在那儿的那个件**。它是三种失败签名里最像自家 bug 的一种：

| 读回 | 意思 |
|---|---|
| `reads ''` | 件根本没落位 |
| `reads '?'` | 落位了，但认不出（半透明面板歧义 → 转视角重读） |
| **`reads <旧件>`** | **手势到了，游戏没接** |

2026-08-04 读日志得出的结论是「mp5k/scope_4x 那两次是本项目的 bug，采集轮自己装了红点又标错了」，写进了 `attachment_catalog` 的注释。**那是错的，2026-08-05 推翻。**

推翻它的不是更仔细地读日志，是**同场阳性对照**——3.5 分钟内、同一条代码路径、同一个槽、同样的起始状态（刷新器自动配上的红点）：

```
aug  + scope_4x   red_dot -> Upper_ACOG_01_C   ok      journal 489
mp5k + scope_4x   red_dot -> red_dot           MISS×2  journal 490, 491
```

再由 `pixi run drag-log` 排掉几何原因：两次失手都是 `place 1/-`（光标一次定住）、`grab±0`（落点零偏差）、`plate 889->898`（枪没掉）。**手势干净而游戏不接 = 拒绝**，`mp5k: {scope_4x}` 因此进了 `EXCLUDE`。

**这正是日志把几何和结果记在同一行的理由。** 一份只说 `ok=False` 的记录，对「游戏拒绝」和「点歪了」给出的是同一句话。

⚠ **而红点是刷新器自动装的，不是采集轮装的**——「刷出来的枪不是裸枪」这条早就写在 `tools/CLAUDE.md` 里。昨天那句被推翻的话，是把一条已知的游戏行为误读成了自家代码的失误。**看到熟悉的 bug 形状之前，先问它是不是一条已经记过的游戏机制。**

⚠ 这条路上我连错三次，每次证据当时都成立：「模板混了 SMG 弹匣」（`ext_smg` 槽位 20/20、margin 10.69）、「PUBG 不给已占用的弹匣槽换装」（日志 magazine 18/68 而其余槽 65/65，看着像分类性的）、「vector 不收 ext_smg」（槽读的是 `?`，既不是旧件也不是空）。

**2026-08-05 有人盯着屏幕重做了一遍：孤立地做，右键装弹匣槽 6/6。** mp5k + `ext_smg`，每次读回、每次复位：

```
#0  Magazine_QuickDraw_Medium_C -> Magazine_Extended_Medium_C   ok   ← 换掉已占用的槽
#1..#5  (空槽)                  -> Magazine_Extended_Medium_C   ok
```

`#0` 当场证伪上面第二个假设——**已占用的弹匣槽换装是好的**。而 `kit_facts` 上那 6 笔 `mp5k magazine ext_smg` 失败因此**是假的**，已销账。

⚠ **所以右键和拖拽现在是同一个形状，而这才是该记的东西**：

| | 孤立探针 | 真采集器 |
|---|---|---|
| 面板到面板的拖拽 | 22/24 = 0.92 | ~0.5 |
| **弹匣槽右键** | **6/6** | **18/68** |

**两条路都是「单独做没问题，采集器里坏」，所以肇因不在手势本身，在手势之间夹着的东西**——装配、切枪、转视角、开关面板。盯屏看不到它：屏幕上那一下是干净的。能回答它的只有 `tab`/`hold`/`click` 都进日志之后、真采集器跑一轮出来的那张「每次失手前的两个手势」表。

### ✅ 2026-08-07 破案：**差别不在手势之间，在于探针只装一次而采集器会重试**

上面那句「肇因在手势之间夹着的东西」列对了现象、猜错了方向。答案就在那张表的措辞里：**探针 6/6 是六次独立的装配，采集器的 68 次里混着重试。**

`right_click_equip` 原来是这样的：

```python
x, y = self.point_of(src)          # ← 循环外算一次
for attempt in range(retries + 1):
    self.pointer.right_click_at(x, y)
```

第一次右键**是成功的**。装进一个已占用的槽会把原件**顶进背包**——背包多一行，底下全部移位。而 `_await` 在 `VERIFY_TIMEOUT` 内没确认（动画还没走完），于是重试，**用的还是那个坐标**，那里现在是刚被顶下来的原件。第二下把它装回去，顶掉这一轮的件。读回看到原件，报「这把枪不吃 ext_smg」，写进 `kit_facts.json`。

**所以那 18/68 里，失败的多数不是没装上，是装上了又被自己装回去了。**

用户盯屏看到的顺序就是全过程，一个字不差：「**好像是装对了，然后又装一次，装错了，然后说找不到，把枪扔了**」。

修法有两半：重试前**按件名重新找行**；找不到就**先问槽位**——第一次可能本来就成了，只是读回慢了，那种情况直接判成功返回，不再点第二下。

⚠ **这是同一个 bug 类当晚的第三次**（另外两次：`ensure_kit` 一次规划全部步骤然后顺序执行；`Kit._swap_back` 读一次背包然后逐行点）。三次的表面症状**都是**「拖拽失败」，三次的日志几何字段**都是**干净的——因为手势本来就没问题，错的是目标。**症状指向错误的方向**，所以配了棘轮：`pixi run gestures`，重试循环里的手势坐标必须在循环内算，或者写下 `RETRY-SAFE: <为什么这里不会移位>`。`drag()` 因此补上了行地址那一半守卫（槽位那一半 2026-08-04 就有了，行那一半一直缺）。

### ⚠ 而修完之后暴露出第二层：那段「换个背景再读」的代码从来没换过背景

第一层修掉以后，同一个格子的失败信息变了形状——从 `reads 'Magazine_ExtendedQuickDraw_Medium_C'`（装错了件）变成 `holds something the templates cannot separate`（读不出是哪个件）。也就是上面「读不出 ≠ 没装上」那节说的 AMBIGUOUS，而它的修法 `AMBIGUOUS_REREADS` 就在 `ensure_kit` 里跑着。

**它在空转。** `_nudge_backdrop` 在 **Tab 开着**的时候发 raw counts，而本文件自己记着「Tab 开着时转视角的 raw counts 打在光标上」——`ViewDriver.turn()` 正因为这个才先关 Tab。那段函数的文档字符串引了同一个事实，却推出了错的结论：**「所以动作要小」，而不是「所以动作没发生」**。而它 `return True` 只检查了 Pico 对象存在。

槽位块的平均绝对像素变化，600 counts 偏航，每臂 4 轮，**带一条 `still` 对照臂**——没有那条臂就只能答「变了没有」，答不了「到底动没动」：

| | 修前 | 修后 |
|---|---|---|
| **still**（完全无输入，噪声底） | 0.32 | 0.21 |
| **nudge**（它实际做的） | **0.29** ← 低于噪声底 | **19.44** |
| **turn**（同样 counts，Tab 关着） | 22.78 | 19.91 |

`still` 这一臂是判据能否定的原因：面板背后的世界有天气、草和别的玩家，问「变了没有」恒为是。三臂只差一个自变量（Tab 开/关），所以 0.29 对 22.78 说得出话。

**代价是 2026-08-05 的那 11 格白丢了**——当时写的修法是对的，只是从来没运行过。这一节和上一节合起来是同一课的两面：**一个「已经修好」的东西，和一个没实现的东西，从外面看一模一样。**

### 面板到面板的拖拽，曾经是这一层唯一不读回的路径

`drag()` 里那条 `if not checks: return ok=True` —— 目标是**面板**而不是槽位时没有槽可验，于是松手瞬间报成功。**12 件配件清库存，12 次 `dragged`，0 件移动。** 铁律破在这里，所以调什么参数都是在赌。

现在按 `docs/game_quirks.md` 早就写好的办法验：**数目的地面板的行数**。`detector.tab_items.panel_rows()` 只跑 Laplacian 占用判据、不做模板匹配，~1 ms，而且**对没有图标的配件同样有效**——采集新配件时正需要这一点。判据是「源列表少一行**或**目标列表多一行」，两边取或：12 行的窗口在背包更满时不会缩，而目标满了不会涨，两者不会同时不动。

实测（`clear_inventory` 六件，每轮）：

| | 结果 |
|---|---|
| 没有读回 | 6 次拖拽，**0 件移动**，报 6 次成功 |
| 有读回 | 6 次拖拽，**清零**，2–3 次重试被自动吸收 |

### 两个旋钮的地线

| 旋钮 | 值 | 地线 | 在哪 |
|---|---|---|---|
| **每步位移** | 32 px | 35 px 还行，**52 px → 1/3，104 px 一跳 → 0/3** | `press/pointer.py: DRAG_STEP_PX` |
| **松手后静止** | 0.25 s | 0.10 s 时每 6 次要重试 5 次；0.25 s 只重试 1–3 次 | `control/inventory.py: DROP_WAIT` |

**悬崖正好在人手的上限上。** 录了 34 次真人拖拽（1 kHz 采光标；那个录制脚本已经不在盘上，**下面这三个数就是它留下的全部**）：每次更新中位 **18–25 px**、最大 **51**、间隔 7.7 ms。而旧代码的 `DRAG_STEPS = 10` 是**固定步数**，1600 px 的 库存→附近 每步 160 px，三倍于悬崖——**那条拖拽从来没成功过**。现在按距离算步数。

**释放点只要越过两栏之间那条虚线**：`附近` 到 x=880、`库存` 从 x=907 起，870 是第一列，从 库存 行 0 过去 **104 px**（旧的固定点 (744,570) 是 437 px）。y 用抓取那行的 y，**不需要找空行**。

### 光标定位：`SetCursorPos` 之后要**重放到稳住**，不是等一个固定时长

`Pointer.place()` 反复 SetCursorPos 直到读回一致（自由态 6 次 × 0.12 s，按住时 3 次 × 0.04 s——必须远短于 `DRAG_HOLD_MS` 0.4 s，否则按键先到期，东西掉半路）。

**为什么固定 sleep 救不了**：Tab **开着**时，转视角的 raw counts 打在**光标**上而不是视角上，而那些 HID 报告是**陆续到达**的。实测（Tab 屏上，分三段排除「固件在注入」「click 报告带位移」「游戏在松手时归位」）：

| | 光标漂移 |
|---|---|
| `move(900,0)`，Tab **关着**（`turn()` 的假设） | (0, 0) |
| 同样的 `move(900,0)`，Tab **开着** | **(450, 0)**，且在之后约 1 秒里逐步累积 |

`turn()` 本来就先关 Tab 再 move，但**关 Tab 的按键会被吞**（`docs/game_quirks.md`），一被吞整轮转视角的 counts 就落到光标上。旧代码「SetCursorPos → 固定等 120 ms → 检查一次 → 按下」，于是在**检查通过和按键按下之间**被推走：报出来是 `released at (946,186), not (870,199)`，差 76 px 正好把东西丢回原来那栏。

验收是**故意注入**一次 `move(900,0)` 再拖：修复前 drag **0/4**，修复后 place **3/3**、drag **3/3**。

### 每个手势都写一行 —— 而且要给别人看

`calibration/artifacts/drag/journal.jsonl`，**常开**，几百字节一次，读它是 `pixi run drag-log`。这里只记两件本层特有的，其余用法在 `tools/CLAUDE.md`：

**一、写日志的是驱动方，不是被驱动方。** 这个文件多个 agent 共写，所以每行带 `pid` / `proc` / 墙钟 `t`。别人那轮采集回来是空的，去看他这几行——**静默失败的运行不会自己打日志**，而这一层替他打了。

**二、2026-08-05 之前只记 `drag`，赔钱的却是 `click`。** 右键打在空槽上会穿到武器行、整枪掉地上（见 `unequip` 那节），而 `right_click_equip` / `right_click_unequip` / `auto_equip` / `drop_weapon` 当时全都直接调 Pointer，一行都不留。现在六种 `kind` 都写：`drag` / `click` / `drop` / `refused` / `tab` / `hold`。

- **`refused` 记的是没发生的失败。** 这一层的闸（空槽、读不出的槽、不在 `MOVES` 里的移动）每一道背后都是一把枪，一份只记「做了什么」的日志看不见哪道闸救了场。
- **`tab` / `hold` 记的是手势之间发生的事**，只在真按了键时才写。下一节那条未破案线索缺的正是这个——探针复现不出采集器，差别就在突发之间夹着的切枪和面板开关。
- **枪名板墨迹 `plate` 是前后两个数**，凡是打向枪或枪槽的手势都带。理由是它答的问题别的字段答不了：右键卸完配件槽位读回是空的，**枪掉了也是空的**，两者从调用方看完全相同，只有墨迹 679–901 → 0 能分开。汇总把这类单独提到最前面、标 ⚠GUN LOST，要 grep 的词是 `gun_lost`。

⚠ **`gun_lost` 只报不修。** 那一步 `cleared` 是真的（槽确实空了），所以返回值仍是 `ok=True`，调用方是照着这个写的。丢了枪之后该怎么办（重刷？弃掉这一轮？）是知道上下文的调用方的事。记录里多一个 `rec['gun_lost']`，日志里多一行，仅此而已。

⚠ **`click_at` 在光标没定住时照样发。** `drag()` 是按下之前就中止的，右键不是——这个不对称没人辩护过，只是没动过它，而它恰好就是「打偏 76 px 落到武器行」的那条路。现在至少落点被记下来了（`place.grab.ok` false + `got.grab`），下一个人不用重新推。

### 手势干净但游戏不接 —— 两个假说都已证伪，答案在**突发内的位置**

症状（`pixi run drag-log`）：成功和失败在手势层面**逐项相同**——`place 1/1`、`grab±0`、`rel±0`、`drag_s` 0.527–0.529——区别只有结果：成功 `polls 1`（0.1 s 内行数就变），失败 `polls 10`（整秒纹丝不动）。**没有中间态，不是慢是没发生。**

**✗ 假说一：固件只在「有变化」时发报告。** `press/firmware/src/main.c: send_hid_output` 确实有 `if (mx==0 && my==0 && rdx==0 && rdy==0 && !buttons_changed) return;`，而 `drag` 的行程是 SetCursorPos 做的、**不经过 Pico**——所以游戏的 raw input 一次拖拽只收到「按下、松开」两个报告，中间零移动。机制是真的，**但游戏并不需要它**。A/B（交替分组，避免被突发内位置混淆）：

| | 每次单独刷件再拖 | 一次刷 6 个连着拖 |
|---|---|---|
| 不发 raw 报告 | 8/8 | 11/12 |
| 每步发一个净零的 raw 抖动 | 7/8 | 11/12 |

`DRAG_NUDGE_COUNTS` 保留为参数、默认 **0**，注释里写着这段，免得下一个人发现 `send_hid_output` 吞掉行程之后再花一晚上。

**✗ 假说二：释放点落在附近栏已占用的行上。** 与 raw 报告无关地独立失败，但连着拖 6 次的数据不支持它——同一个释放点、同样的地面栏，第 1 次挂、第 2..6 次全中。

**✓ 现在指向的：突发内的位置 + 目的列表的状态。**

```
burst 1  6/6      burst 3  #1 MISSED (rows 6->6)，之后 5/5
burst 2  6/6      burst 4  #1 MISSED (rows 6->6)，之后 5/5
```

**只有每个突发的第一次会挂，而且只从第三个突发起。** 唯一单调变化的量是地面栏的行数（每轮涨 6，第三轮起超过 12 行的窗口）。真实采集器里更严重（9/18），因为它一直在连着拖。

⚠ 探针 22/24 = 0.92 而采集器 0.5，**探针还没复现出采集器的失败率**——差在采集器的突发之间还夹着装配、转视角、开关面板。下一步是让探针把那些也照抄进去，而不是继续加假说。

**2026-08-05 起不必再靠假说了**：`tab` / `hold` / `click` 现在都进日志，`pixi run drag-log` 最后一段直接打印「每次失手前的两个手势」。真采集器跑一轮，那张表就把「突发之间夹着什么」从推测变成计数。

### 这一节里有两个结论是被推翻过的，写下来是为了别再推一遍

- ⚠ **「往已占用的行上放会失败」——假的。** 来自「连续拖 3 次、末尾统一读回」的测法，稳定 2/3。那 1/3 跟落点无关，是缺少间隔。同样落点逐次读回 5/5、6/6。
- ⚠ **「drop 可以降到 0.10，扫描显示全平」——也是假的**，而且是同一个错误的第二次发作：扫描脚本每次拖前调了 `look()`（~123 ms 全量检测，期间光标不动），把被测变量当常量喂了回去。真实调用里没有任何东西隔开两次拖拽。

**测手势必须让测量循环本身不提供间隔**，否则测出来的是测量方法，不是游戏。

⚠ **「右键只够得着手上那把枪」这条在单枪场景下被证伪**：不 `hold()` 也是 5/5。机架里有两把枪时要不要按 1/2 指定目标，**没测过**——需要指定时仍然 `hold()`，但别把它当成右键能不能落位的前提。

**`drop_weapon(gun)` 扔的是整把枪，配件跟着走。** 目标是枪械行左端那个方框数字（`at_gun(n)` → `gun_tag_point`，实测 (2237,145)/(2237,447)）。两个手势都行，**默认右键**：

| 手势 | 落位 | 端到端 |
|---|---|---|
| 右键点一下（默认） | 1/1 | **0.66 s** |
| 向左拖 1621 px | 1/1 | 1.15 s |

两次实测（2026-08-02，同一把 aug 带 4 件）都是：机架清空、**库存零增长**（配件确实跟着走了，没掉回背包）、地面多一行。`gesture='auto'` 先右键、不成再拖；`'click'` / `'drag'` 强制其一。

为什么不先 `strip()` 再扔：拆下来的配件会回到背包，而 PUBG 会把背包里能装的**自动装到下一把枪上**——一轮标着 BARE 的数据就是这么带着握把和快拉弹匣跑完的。整枪扔出去，下一对枪才是干净的。

**能力矩阵是数据不是散文**：`MOVES[(src_kind, dst_kind)]` 说得出手势、能不能读回验证、以及**证据等级**（`measured` / `used` / `untested`）。`_reject()` 拿它当闸门——两端都是合法地址不代表这个动作存在，`('gun','inventory')` 就是两个好地址加一个不存在的动作。

**每个方法只返回两种形状之一**：`step()`（一个手势）或 `batch()`（一批，带 `steps`）。以前是五种。`ensure_kit` 的 `ok` 由读回决定，比「每步都 ok」更强，用 `batch(ok=...)` 表达。

`transfer(1, 2)` **故意走背包中转**：直拖 slot→slot 那条边在 `MOVES` 里标着 `untested`，而隔壁实测是「库存拖进枪槽 0/4」。要定它：直拖 N 次，**两端都读回**——源槽空 且 目标槽满。只读源槽分不出「移过去了」和「掉地上了」。

地址体系（`pixi run locations` 有 81 项离线回归）：

| 地址 | 是什么 |
|---|---|
| `at_gun(n)` | 枪**本身**（`('gun', n)`）|
| `at_slot(n, s)` | 那把枪的某个配件槽（`('weapon', n, s)`）|
| `at_inv(i)` / `at_ground(i)` | 库存 / 附近的第 i 行，`i=None` 表示「这个面板里随便哪」|

⚠ `at_gun(1)` 和 `at_slot(1,…)` 是**两种不同地址**，别混。`_reject()` 一度不认识 `('gun', n)`，于是每次扔枪都在鼠标动之前就被拒（报的却是「拖拽失败」），而地址、抓取点、方法全都写好了——那个 bug 活到有人写离线测试为止。

### 对局内回路

`match.py` 的 `Dispatcher` 由 `robot.py` 装配，不要单独 new。它读 `config` 里的表：`KEY_ACTION_TABLE`（按键→状态+硬件）、`DETECT_TABLE`（调度检测器）、`MISMATCH_TABLE`（调度训练数据采集）。

**加新行为优先改配置表，不要往 `_loop` 里塞分支。**

采集本身在 `calibration/mismatch.py`——这个回路要赶发 pattern 的时机，不该在里面写 PNG。

## 顺序是铁的：**腰射 → 动镜头 → 开镜 → 取参考**

```python
rig.gun.ensure_hip()                          # 1
rig.view.goto_midline(posture, set_ref=False) # 2  ← set_ref=False，不是默认
rig.gun.ensure_ads()                          # 3
rig.view.set_reference()                      # 4
```

`calibration/collect_timed.aim_and_scope()` 是这四步的唯一实现，**要动视角就调它，别自己拼**。换个顺序会同时坏三样东西，而且三样都不报错：

| 步 | 换了顺序会怎样 |
|---|---|
| **1 腰射里动** | 俯仰是**角色**的属性，两个硬限位在任何镜子下都是同两个；跟着镜子变的只有「一个 count 转多远」。开着镜瞄准就把 `pitch_scale` 拖了进来——那是个**没验过的模型**，2026-08-05 每一次倍率镜尝试都栽在它上面。腰射量一次行程，所有镜子共用 |
| **3 摆好了再开镜** | 开镜是 toggle + 动画。视角还在稳的时候把镜子抬起来，它就在测量里面稳 |
| **4 参考最后取** | 跟踪器的 patch 是**按镜子分的**——红点七列、VSS 的 PSO-1 三列。腰射态取的参考描述的是这一梭**永远不会再经过**的画面。`goto_midline` 默认在末尾取一次，所以这里必须传 `set_ref=False` |

⚠ **`collect_timed` 曾经是反的**：先 `ensure_ads()` 再 `goto_midline()`，也就是**开着镜把视角挪到中线**，参考也在那时取。三样里坏了两样，而每一梭都跑完了、每个数都印出来了。

## 每个弹匣打之前：**在腰射态**低头到底，然后抬头到中线

**三档瞄准状态的定义在 `detector/CLAUDE.md`**（腰射 / 肩射 / 开镜），这一层只说怎么到达：`ensure_ads()` 进开镜，`ensure_hip()` 回腰射。

⚠ **`ensure_hip()` 的保证来自「松开右键」这个动作，不是来自读回。** `in_ads()` 答的是「开没开镜」，而腰射和肩射的答案都是「没开」——所以它先发一次释放再验证。**这个不对称是四轮 K 标定跑在肩射里、文件名却写着 ADS 的直接原因。**

**为什么定俯仰要回腰射。** 俯仰是**角色**的属性，两个限位在任何镜子下都是同两个；跟着镜子变的只有「一个 count 转多少度」，而那个换算（`pitch_scale`）是没验过的模型，8-05 每一次倍率镜尝试都栽在它上面。**在固定的一档里做这个动作，换算就整个不进来**——腰射行程量一次，所有镜子共用，而不是每个镜子量一次。

**实测（2026-08-06，m416 站立，`calibration/artifacts/pitch/pitch_travel.json`）：**

```
腰射   行程 8034 counts   区间 (7725, 8034]   中线 4017    上/下行差 309 = 一个步长
红点   行程 3400          （08-04 实测，口径修正后）      中线 1700
比值   8034 / 3400 = 2.36        而 pitch_scale 说 3.095 —— 模型偏高 31%
```

**「中点即水平」的验收是两张图，不是一个数**：`standing_level.png`（腰射，抬 4017）地平线在屏幕中心上方 **58 px**，`standing_level_0804_red_dot.png`（红点，抬 1725，人眼确认过）**60 px**。**两个档位、隔两天、不同走法，落在同一个俯仰上，差 2 px。**

⚠ 同一轮还报了 `count ruler: tracked/commanded 0.636 ± 0.095`，**标着 not flat**。腰射档 counts→画面位移不是常数——**但中点不受影响**（只要单调，半程仍是半程）。它挡的是任何拿腰射 K 做绝对换算的说法，`config.py` 那条 `hipfire ~0.50 (TPP, no weapon)` 的告警仍然有效。

代价两条：每梭多一次带验证的 toggle；**参考图必须在镜子抬起来之后再取**——跟踪器的 patch 是按镜子分的，腰射态取的参考描述的是这一梭永远不会经过的画面。



**`ViewDriver.goto_midline(posture)`。** PUBG 的俯仰在正下和正上各有一个硬限位，所以**两个限位的中点就是水平**——跟地形无关、跟镜子无关、跟姿势无关。这是这一层能对「视角指哪」做出的最强陈述。

它替掉了两个都被实测否掉的做法：

| 旧做法 | 怎么错的 |
|---|---|
| `goto_pitch_centre` | 瞄**可跟踪带**的中点，而那条带跟着角色朝向跑（一轮 800..2200，下一轮 100..2100）。两格瞄在不同俯仰上测出不同后坐力，谁都没记是哪个 |
| `goto_level` | 按**存下来的**每姿势偏移抬头，再乘 `pitch_scale()`。红点站立没问题；2026-08-05 每一次倍率镜尝试都扎在角色自己脚面上，而且每次是不同的单位错误 |

**半个行程不依赖任何一个信念**：一个硬限位（游戏给的唯一绝对量）、一个本轮自己量出来的行程（当前镜子的原始 counts）、一条游戏性质（两个限位对称）。

⚠ **限位测不到，靠的不是视角跟踪器。** 相位相关在两个限位处都是瞎的——下面是贴脸的裸地，上面是空白天空——而**瞎读出来是「没动」**。第一版这么写，报出来游戏整个俯仰行程 13 counts。判据是**中央裁图的原始帧差**，每一步自带两个对照（`control` = 同一俯仰下什么都不发时它自己变多少，`predict` = 真动了本该变多少）。常量出处和那次把标准差当阈值的实测都在 `control/aim.py` 顶部的 TRAVEL 段。

⚠ **上下是两趟独立测量，而瞄准只认「上」那一趟。** 第一趟往下走到底（counts 丢掉，起点未知）、第二趟从下限位往上、第三趟从上限位往下。`goto_midline` **只会从下限位往上推**，所以它要的量是「往上走完整个行程要多少 counts」——而游戏两个方向吃 counts 的比率不一样（K 的上下不对称实测 **5.37%**，53% 那次是屏幕上有界面的伪迹）。3450 上摊 5.37% ≈ 185 counts，两个区间直接错开；**平均掉的话中线偏低约 gap/4 ≈ 46 counts**。所以下行那一趟改当**对照**：两趟差超过一个 step 就打印百分比并落 `agreed: false`，等于顺手把上下不对称按镜子量了一遍。

⚠ **区间方向以前是反的，两个文件都反。** 走到 `T` 那一步动了 ⟹ 走之前还没到限位 ⟹ 行程 > `T-step`；下一步不动 ⟹ 已经在限位上 ⟹ 行程 ≤ `T`。**所以区间是 `(T-step, T]`，而旧代码写的是 `(T, T+step]`——整整高一个 step，而且它把限位放在了「视角已经确认到过」的位置之外。** 点估计取区间**上端**而不是中点，理由是实测的：游戏只吃约 60% 的 commanded counts，而 `predict` 是按满步算的，所以最后一个残步大约交付一半就会被判成 moved。

对得上独立的那个数：实机站立旧口径报 3450 ⟹ `T = 3400` ⟹ 半程 **1700**，而 `fit_pitch_level --from-spawn` 从进场（游戏自己摆的水平）往下量出来的 `level_up` 也是 **1700**。旧口径下这个吻合差 25。

⚠ **行程按姿势存，这条不直观。** 站立和蹲下都是 3450 counts（一个数不差），**趴下只有 1450**——游戏把趴姿的俯仰裁了。所以半程只在前两个姿势上被证明是水平；趴姿的中线仍然是最可重复的起点（相对硬限位的固定偏移），但**没有证据说它是水平**，`goto_midline` 每个姿势提醒一次而不是让人默认。

⚠ **`tracking_lost` 要在归位之前读。** `goto_midline` 末尾会 `set_reference()`，而那会清掉这个标志——写在它后面的检查永远不会触发。归位成功本身就是恢复（回的是硬限位，不是跑偏的累加值），所以现在是「归位前记下来，归位成功就报告已恢复，归位失败才放弃这一格」。

**离线验收**：`python tools/probe_pitch_range.py --selftest`。那个 `_FakeRig` 现在套的是**真的 `ViewDriver`**（`world_fn` 是唯一的接缝），所以它测的正是采集会跑的那条路——包括 `goto_midline` 从三个不同起点（含顶死在上限位）的落点。

⚠ **那个 fake 到 2026-08-06 为止上下是对称的，所以它分不出「取上行」和「取平均」，两个规则一起放行。** 加了 `up_gain` 之后（3 组：0.95 / 1.05 / 0.947），判据换成**视角最后实际停在哪**而不是发了多少 counts。**把旧规则贴回去跑过一遍：3 组里挂 1 组（+75 counts）**——只写一组的话照样放行，这就是「闸门要两侧都验」的又一次现场。

## 换弹等到什么时候：看子弹数字，不是看计时器

`FireDriver.wait_reload(expect)`。给了 `expect`（弹匣容量）就在数字回到它的那一刻返回——**这是游戏自己说的，不是推的**。`top_up()` 不知道容量（它就是量容量的那一步），规则放宽成「大于零且不再变化」。

替掉的是「二值化弹药区、等像素不动、再固定睡 1.8 s」。像素说不出动画走到哪了，数字说得出。

⚠ **那 1.8 s 是在付一笔真账**，别当成冗余删掉就完了：**换弹动画期间 PUBG 不收右键**（m416 四个弹匣实测，计数停跌后 2000 ms 点 0/4、2300 ms 3/4、2400 ms 4/4）。现在敢不付这笔钱，是因为**要它的那一方本来就是闭环的**——`ensure_ads` 会重试，被吞掉的一次点击代价是再点一次，不是一个腰射的弹匣。**万一这个判断错了，症状是每次换弹后第一个弹匣 `ads_frac` 偏低**，而那个闸门本来就逐弹匣报数。

数字读不出来的枪仍走像素兜底，**并且会打印一行说自己降级了**——「像素静止」比「读到 30」弱得多，一轮采集不该能悄悄拿弱的那个。

**开镜确认之后再等 0.5 s**（`ensure_ads(settle_s=ADS_SETTLE_S)`）。判据是准星消失，而准星是开镜动画里**最先**没的东西——踩着那个沿开火，画面还在动。只在**真点了右键**的那条路上等：本来就开着镜就没有过渡，没什么可 settle 的，而这个函数一格要调好几次。0.5 是沿用 `ADS_SETTLE_S`，**准星消失那一刻动画还剩多少没人量过**。

## 共用硬件

多个 agent 共用**一个 Pico 串口**和**一个游戏窗口**。跑之前查有没有别的 python 进程占着，**别杀别人的**：

```python
from press.pico_mouse import other_agents
```

**`Pointer` 是懒构造的**——只读状态的调用方不会去占串口。别在构造函数里提前建它。

⚠ 这句话在这个文件里写了几个月，**四个驱动类里有两个违反它**（`SpawnerControl` / `InventoryControl` 都在 `__init__` 里建 `Pointer`）。代价实测：

```
>>> sc = SpawnerControl(verbose=False)
[pico] connected on COM10
```

而 `sc.plan()` 是文档点名的**纯离线**入口（「想先看它要点哪，不碰游戏」），`ensure_ready()` 每次也建一个 SpawnerControl 只为问面板关没关——**两个都在抢那个多 agent 共用的串口**。

现在四个类都继承 `control.driver.Driver`，`pointer` 是懒 property，`can_press` 一份，`close()` 释放句柄（**不关那个共享的 mouse 单例**——那会把设备从别人的运行里拿走），`with` 真的走 `close()`。**规则 11 管着**（`pixi run layering`）：`control/` 的类不许在 `__init__` 里建 `Pointer`。

⚠ **`Driver` 和四个子类 2026-08-08 起都不收 `backend` 参数了。** 它从 `Driver.__init__` 一路穿过四个子类、六个 `--backend` CLI、十处使用点，只为把一个常量送到一次 `Pointer()` 调用——它选的那个 SendInput 后端在 PUBG 下点不动、转不动、开不了火（理由在 `press/CLAUDE.md`）。`can_press()` 留着，因为「第一秒就知道这轮能不能跑」的价值还在，但语义换了：现在没 Pico 是 `Pointer()` **抛异常**，`can_press` 捕获它、**把原因打印出来**再返回 `False`。⚠ 不吞——「另一个 agent 占着 COM10」和「没插线」是同一个 `False`，而操作员要做的事相反。

⚠ 最能说明问题的不是那两处急建，是 `SpawnerControl.__exit__` 的注释——它写着「Nothing to release: **the Pointer is lazily built**」，而建它的那一行就在**上面 23 行**。注释描述的是有人想写的代码。

要跑占用游戏焦点的东西，**先跟用户说一声等确认**。失焦会让整轮数据静默归零，而且看不出来。
