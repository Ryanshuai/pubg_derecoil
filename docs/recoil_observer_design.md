## 1. 观测方程

```
Δview  =  player_input  +  comp_injected  +  recoil_kick
```

移项得到真正要的量：

```
Δview − player_input  =  comp_injected + recoil_kick  ≡  压枪残差 e
```

`e > 0` 压枪不足（枪往上飘），`e < 0` 压过头。**不需要知道 comp 是多少**，只需要屏幕位移和玩家原始输入两个量。这把 Pico 遥测的需求砍到只剩「回报玩家原始 delta」。

⚠ **原文这里写:「更新律是积分器 `dy[i] ← dy[i] + η·e[i]`，即迭代学习控制（ILC）。`pico_mouse.py` 里手调的 `RECOIL_LEAD_FRAC = 0.30` 对应 ILC 的相位超前项，可从数据辨识。」三样东西现在都不在了:**

- **那个 `i` 是弹号**,而拟的是 `y_true(t)`——时间的函数,固件播的也是这个。
- **那个积分器有增益**,而现在是全库一次性拟合:没有 α、没有轮次,「这一格收敛没有」这个问题不存在。⚠ 这不是风格取舍——根 `CLAUDE.md` 记着一个带增益的回路配上一次残差平滑,把逐发振荡放大了 **1.025²⁵⁵ ≈ 540 倍**。
- **`RECOIL_LEAD_FRAC` 已经删了**,取代它的是 `config.RECOIL_FIRE_DELAY_MS = -19`(`MODEL.md` 三的 `D`),而且它**不进拟合**。

上面那个观测方程本身没变,它就是 `MODEL.md` 的 `y_true(t) = y_obs(t) + C(t − M)`。

## 2. ROI 位置：必须贴屏幕垂直中线

纯 pitch 旋转 θ 下，像素 (x, y)（相对主点）的位移：

```
Δy = −θ·f·(1 + (y/f)²)        垂直增益随 y 偏移放大
Δx = −θ·(x·y/f)               垂直后坐力漏进水平读数
```

`crosstalk = |dx|/|dy|`，实测 (f=1100)：

| | x=200 | x=500 | x=900 | x=1300 | x=1700 |
|---|---|---|---|---|---|
| **y=0** | 0.1% | 0.2% | 0.4% | 0.5% | 0.7% |
| y=200 | 3.1% | 7.8% | 14.1% | 20.3% | 26.5% |
| y=500 | 6.8% | 17.0% | 30.5% | 44.1% | 57.7% |

y=0 时 gain 恒为 1、串扰 <1%，**且与 f 无关**——所以贴中线可以完全免掉 tan 校正和焦距标定，只剩 K（px/count）一个待标定量。

比数值更本质的理由：**phaseCorrelate 假设纯平移**。patch 内部一旦有 gain 梯度，实际变换是仿射的，纯平移模型就有偏，这是相关峰本身的污染，事后标量校正补不回来。

> 注：`crosstalk ∝ x·y`，所以屏幕**正上方/正下方**（x=0）的垂直带串扰同样为 0，只是 gain 需要按 f 校正。4x 倍镜空间不够时这是备选，见 §6。

**结论**：观测带 `y = 656 .. 784`（128 高，中心 720）。

⚠ **高度后来翻倍了**，理由在 §3.1 的量程那一栏：`config.RECOIL_BAND_Y = 592`、`RECOIL_PATCH_H = 256`，实际带是 `y = 592 .. 848`，仍然以 720 居中。**贴中线这条结论不变**（它是关于 y 偏移的），变的只是带宽。

## 3. Patch 尺寸：四个约束的交点

### 3.1 量程（用户关切：后坐力大时匹配不上）

实测崩溃边界（真实截图，整数行平移）：

```
 shift    误差        备注
    16   +0.10
    32   +0.18       P/4
    48   +0.28       3P/8 — 实测仍然准
    64  +128.28      P/2 — 完全崩，FFT 循环混叠
    80  +128.56
```

**安全范围 3P/8 = 48 px（P=128）**，比理论 P/4 宽松。崩溃形式是**符号翻转**而非随机值，可检测。

每帧位移估算（一发子弹的 kick 约 30ms ≈ 4.3 帧 @144fps）：

| K (px/count) | 每帧位移 | 场景 |
|---|---|---|
| 1.0 | 2.9 px | 低灵敏度腰射 |
| 2.0 | 5.8 px | 典型腰射/红点 |
| 4.0 | 11.6 px | 2-3x |
| 8.0 | 23.1 px | 4x |

4x 下 23px < 48px 安全线，**128 够用**。但玩家同时甩枪会叠加，必须配预测偏移（§3.5）。

### 3.2 误匹配（用户关切：截图太小容易误匹配）

在强周期纹理（栅栏/砖墙/瓷砖）上测 10px 位移：

| patch | period=16 | period=32 | period=64 |
|---|---|---|---|
| 64 | +0.16 | +0.01 | +0.21 |
| 96 | +0.16 | −0.00 | +0.01 |
| 128 | +0.03 | −0.03 | −0.03 |
| 192 | +0.04 | +0.02 | +0.00 |

**实测不成立**——即使 64px patch 在周期纹理上也没有 aliasing 到错误峰。phase correlation 用全部像素的相位投票，比稀疏特征点鲁棒得多。这条约束可以放松。

### 3.3 成本（用户关切：截图太大速度有问题）

```
patch    1个      ×4      占144fps帧预算    批处理288帧×4
   64   0.044   0.175        2.5%           0.05 s
   96   0.104   0.416        6.0%           0.12 s
  128   0.162   0.647        9.3%           0.19 s
  192   0.659   2.635       37.9%           0.76 s
  256   1.109   4.436       63.9%           1.28 s
```

**关键：成本不是约束**。捕获线程只做切片+存储（**0.015 ms/帧**），FFT 全部推到停火后的 worker 线程，预算是「一个弹匣」而非「一帧」。即使 256×8patch 也只要 2.6s。

架构：

```
capture thread (144fps)   开火期间只切片存储        0.015 ms/帧
      ↓ 松开左键
worker thread             批量 phaseCorrelate       0.2–0.4 s
                          → 减 player_input
                          → ⚠ 按子弹窗口聚合      ← 没有子弹窗口了
                          → ⚠ Kalman 更新         ← 没有轮次了
                          → upload_pattern
```

⚠ **后两步是弹桶坐标的产物。** 现在是「每帧一个样本、`t` = 距点击多久」,直接进样本库,拟合离线做、吃全库。

内存：8 patch × 128×128 uint8 = 131 KB/帧 × 288 帧 ≈ **38 MB**。

### 3.4 patch 内 gain 梯度（决定带高上限）

patch 高 P 时边缘 y=±P/2 的 gain 误差（不可用标量校正，违反纯平移假设）：

| P | f=720 | f=1100 | f=1720 |
|---|---|---|---|
| 64 | 0.20% | 0.08% | 0.03% |
| 128 | 0.79% | 0.34% | 0.14% |
| 192 | 1.78% | 0.76% | 0.31% |
| 256 | 3.16% | 1.35% | 0.55% |

宽 FOV（f=720）下 256 会引入 3% 系统偏差，直接串进 scale 估计。**128 以下安全**。

### 3.5 结论

**P = 128**，四条约束都满足且有余量。

> ⚠ **实际落地是 128 宽 × 256 高**（`RECOIL_PATCH` / `RECOIL_PATCH_H`）。高度按 §3.1 的量程加倍、宽度按 §3.4 的 gain 梯度留在 128——**四条约束里只有量程那条要高，只有 gain 梯度那条怕高，而它们分别管高和宽**，所以两个方向不必取同一个值。⚠ 无歧义范围因此是**半个 patch 高 = 128 px**，而混叠的**步长**是一整个 256 px：两个数不一样，`calibration/calibrate_k.py` 曾经把步长当成上限写进 docstring。见 `MODEL.md` 3.1。

配合**预测偏移**（patch 窗口按上传的 pattern 预移，相关器只看残差）：

```
true=90  pred=85  →  total=89.919   err=−0.081 px
true=60  pred=70  →  total=60.040   err=+0.040 px   (预测偏错方向也没事)
```

预测偏移把有效量程从 ±48px 扩到「预测误差 ±48px」，4x 高 K 场景靠它兜底。

## 4. Patch 数量与投票：4 个不够

实测遮挡下的中位数表现：

```
坏 1 个 / 共 4：  median err −0.06   ✓
坏 2 个 / 共 4：  median err +4.54   ✗  偶数中位数取中间两个平均，被拖走
```

**用奇数个，且 ≥ 5**。空间足够：keepout ±330 时，DXGI box 内可放 10 个 128px patch（左 3 右 7）。

**建议 7 个**，成本 288帧×7×0.162ms = **0.33 s**，捕获切片 0.026 ms/帧。

聚合方式：MAD 剔除离群后取中位数，而非直接平均。

## 5. 失效模式清单

实测数据，`true shift = 10 px`：

| 失效模式 | 单 patch 表现 | 检测手段 | 处置 |
|---|---|---|---|
| **亮度突变**（闪光弹/枪口火焰）| gain×3、+120 offset 下误差 <0.2 px | 不需要 | **免疫**，phase correlation 只用相位 |
| **量程超限** | 符号翻转，err ≈ P/2 | 方向与预测相反且幅度≈64 | 丢弃该帧，或加大预测偏移 |
| **局部模糊**（烟雾/镜外虚化）| 75% 面积→2个崩；100%→全崩 | 梯度能量 + 与其他 patch 不一致 | 丢弃该 patch |
| **实心遮挡**（血雾/UI/命中标记）| 取决于遮挡块能量 vs 真实纹理能量，**不是面积** | MAD 离群 | 丢弃该 patch |
| **局部运动物体**（敌人穿过）| 10% 面积即可崩到测出 0 位移 | MAD 离群；多 patch 一致错时**检测不到** | 见下 |
| **低纹理** | 实测**不是问题**，见 §5.1 | 梯度能量（阈值 ~0.1） | 只挡纯黑/纯白病态帧 |

### 5.1 gate 阈值：比直觉低两个数量级

真实截图整数平移，13 个 patch：

```
gate    0.5  →  worst err 0.07 px
gate   38.8  →  worst err 0.13 px
gate  113.0  →  worst err 0.42 px
gate 1106.9  →  worst err 0.02 px      高纹理对照
```

**gate 分数与精度基本无关**。phase correlation 在频域聚合 16384 个像素的相位，对低对比度极鲁棒。合成实验里「纯色完全失效」的前提是数学常数（std 严格 0），真实屏幕不存在这种区域。

**阈值取 ~0.1，只挡纯黑/纯白/UI 全覆盖等病态帧。**

反面：**不能用 phaseCorrelate 的 response 做 gate**——纯色输入上 response = 0.95（虚高第二名）而位移读数完全错误。必须用梯度能量。

### 5.2 端到端验证：整弹匣注入故障

`temp_debug/demo_audit_plot.py`（⚠ **已不存在**，见文末）用真实截图 patch 模拟一个 AKM 弹匣（432 帧，7 patch），注入三种故障后跑完整流水线：

| 故障 | 误差 | MAD | 被剔除帧 | 自动检测 |
|---|---|---|---|---|
| **F1** 单 patch 被静止纹理块遮挡 | **0.20 px** | 0.007 | 67 | ✅ 剔除生效，误差被完全吸收 |
| **F2** 单帧位移超 P/2 | 128.46 px | 0.046 | 2 | ✅ 仅靠 sign-flip 专门规则 |
| **F3** 全部 patch 被运动物体污染 | **5.75 px** | 0.016 | **0** | ❌ **完全漏检** |
| 干净帧（150 帧） | 0.472 px | — | — | — |

三条结论：

1. **7 patch 冗余对单点故障非常有效**——F1 下坏 patch 被剔除 67 次，最终误差 0.20 px。
2. **MAD 只能抓少数派故障**。F3 里全部 patch 一致地收敛到「零位移」，MAD = 0.016（比干净帧还小），任何阈值都抓不到。误差 5.75 px 恰好等于信号本身，即该段位移**完全丢失**。
3. **F1 的第一次注入用纯色块，没能造成故障**——纯色不携带相位信息，不与真实纹理竞争相关峰。改用纹理块才崩。所以「血雾/UI 遮挡」的风险等级应下调，**真正危险的是有纹理的运动物体**。

缓解手段（MAD 之外的，按优先级）：

1. **累积轨迹对账**：F3 在累积位移曲线上表现为一段平台，之后两条线**永久性平行分离**（本例最终差 ~150 px / 22%）。逐帧看不出来，累积看一目了然——这既是人工复查的主要抓手，也是唯一可自动化的可靠信号。
2. **物理先验**：后坐力不会瞬间归零再恢复。对位移序列做时间域二阶差分门限。
3. **与已知量对账**：`e = Δview − player_input` 若整段统计偏离曲线预测超过 Nσ，弃用该弹匣。
4. **patch 空间分散**：左右两侧各放，单个敌人不可能同时覆盖 x=980 和 x=2620。

## 5.3 实测标定结果（2026-08-01）

`calibration/calibrate_k.py`，设置为常规 30 / 瞄准 50 / 开镜 50、各倍镜滑块全默认 50。

> ⚠ **红点那一行已经被替换,而且是被同一个脚本自己推翻的。** 现值 `red_dot = 1.5413`(`config.RECOIL_SIGHT_PROFILES`,2026-08-08),`MODEL.md` 三把它标 🟡:两个实弹 run 的等效值 1.5416 / 1.5250 夹着它,**差 1.08%,所以有一次是错的**。
>
> ⚠ **而下面这一整张表是在一个已知会混叠的注入速率下测的**:相关器逐对无歧义只到 128 px,当时 480 counts 摊在 0.15 s 上,峰值 124 px/帧,`tools/audit_k.py` 在存下来的红点 run 里找到 **22 行里 8 行是混叠的**,两行相差恰好 256.01。**`max_abs_frame` 看不见它**(混叠的那一对报出来是个小数)。所以这张表的**方法**已经改了:注入摊到 1.0 s。
>
> ⚠ **「上下不对称」这一列不要再拿去用。** 从这批数据推出来的 +6.32% 已被判定不成立,干净测出来是 **0.19%**(`MODEL.md` 6.2)。

| 状态 | K (px/count) | R² | CV | 上下不对称 | 可用 patch |
|---|---|---|---|---|---|
| TPP 腰射（无枪） | ~0.50 | — | — | — | 7 |
| ADS 红点 (1x) | ~~1.5474~~ → **1.5413** | 0.99999 | 0.3% | 0.43% | 7 |
| ADS 2x | 1.8254 | 0.99948 | 2.0% | 2.47% | 3 |
| ADS 3x | 1.8802 | 0.99977 | 1.4% | 0.38% | 3 |
| ADS 4x | 1.8827 | 0.99964 | 1.9% | 0.24% | 2 |

**观测层验收通过**：R² 全部 > 0.999，最好一档达 0.99999 / CV 0.3%，比合格线好一个数量级。

三条结论：

1. **倍镜共用一个 K ≈ 1.86**。2x/3x/4x 彼此差异（σ=0.032）小于各自的测量 CV，是同一个值。1x 低 18%，因为红点/全息/机瞄走「瞄准灵敏度」滑块，2x+ 走「开镜模式灵敏度」×每档乘子。所以只需三个 K：腰射 0.50、1x **1.5413**、倍镜 1.86。

   ⚠ **但表里存的是七个键、逐档一个值**（`hipfire / red_dot / 2x / 3x / 4x / vss_pso1 / p90_integral`），不是三个。⚠ **而 `iron` 仍然不在里面**：**有**镜位而空着的枪映射成 `'iron'`，那是个表里没有的键。以前这种枪拿默认值硬算，2026-08-09 起 `collect_timed` 和 `harness/adapter` 各有一条闸直接拒绝（**在那之前只拒「旗标和读回不一致」，两边都说 `iron` 是放行的**）。

   ⚠ **`p90_integral = 1.5656` 是这张表里唯一按比例得到的一条,而那是故意的。** `calibrate_k` 丢重复帧，所以它累积相关器的每对偏读 b(delta)——`red_dot` 存的 1.5413 因此来自**单对**探针而不是 `calibrate_k`。两个口径的数不可比，但**同口径的两条跑相除，那个乘性偏差约掉**：同一条命令量 p90 和红点，比值 1.0157（50/100 两档，sem 0.16–0.24%），`1.5413 × 1.0157`。300 档按事先定的规则排除（8.4 px/frame，远在真实一梭 p25 0.90 / 中位 2.00 / p75 3.78 px 的区间外），而 200 档在 p75 之外仍然同意——那是「规则不是在凑答案」的检查。**每边只跑了一条，没复现。**
2. **量程担忧解除**。所有档位下真实后坐力只占用 11~12% 的可用量程（安全线 3P/8 = 48 px），余量 8 倍。
3. **patch 数随倍率下降：7 → 3 → 2**，这是当前最大的工程债，见 §6。

垂直灵敏度增强设为 1，所以垂直不需要额外系数。

## 6. 倍镜（4x 必须支持）

**问题**：镜内是放大画面、镜筒外是 1x 虚化环，**两者 K 差约 4 倍**（4x 镜内 1.88 vs 镜外 ≈ 腰射的 0.50），混用直接毁掉标定。且实测虚化区 100% 模糊时 phase correlation 全崩。

### 6.1 实测各档镜内区域（中线上，3440×1440）

| 倍镜 | 镜内圆 x 范围 | 准星宽度 | 应有 keepout | 可放 128 patch |
|---|---|---|---|---|
| 2x | 1344 – 2020 | ~70 px | ±60 | 3 |
| 3x | 1370 – 2150 | ~100 px（含竖线） | ±70 | 3 |
| 4x | 1240 – 2180 | 竖线仅数 px | ±70 | **5** |

三个反直觉的点：

- **镜内圆不是随倍率单调变大的**，2x 的圆最小。
- **keepout 必须随瞄准状态变**。±330 是按机瞄/红点定的（枪身横在中间），但开镜后中心只剩一条细准星，沿用 ±330 会把镜内区大半排除掉——实测 2x 镜内区 x∈[1344,2020] 几乎完全落在原 keepout [1390,2050] 内；4x 沿用 ±330 会把可用 patch 从 5 个砍到 2 个。判断准星宽度用列能量剖面：4x 的竖线在 x=1720 是个 133683 的尖峰，两侧 20px 就掉回 24000，实际只有几个像素宽。
- **倍镜没有光学畸变**。曾怀疑镜内是模拟透镜、边缘 patch 位移不准，实测否定：4x 下离镜心 136 px 与 406 px 的 patch，K 相差 **0.13%**。镜内是平的窗口，patch 可以放在圆内任何位置。残余的 ~2.7% 散布是 trial 间的（注入时序、帧率抖动），五个 patch 完全同步，靠挪位置解决不了。

gate 分数能干净地区分三类区域（4x 实测）：镜内 27000~52000、镜筒黑边 25~57、镜外虚化 1531。**但 §5.1 定的阈值 0.1 拦不住镜筒**（它有 25~57 分），必须改用相对判据或按倍镜切换 patch 布局。

### 6.1b 准星标记污染：条件性故障，单次验证无效 ⚠️

VSS 的固定 PSO-1 实测 K = 1.875，与标准 4x 的 1.885 一致（游戏内部按 4x 处理）。但它的准星占地大得多——横线横跨 `x = 1460..1990`，加上刻度和测距梯形，大片压在观测带上。

**同一个 patch 位置，两轮测出相反结果**：

| 朝向 | patch x=1900 的 gate | std | 判定 |
|---|---|---|---|
| 沙地 + 草 | 3886 | 0.026 | 干净 |
| 岩石（弱纹理） | 1123 | **0.777** | 崩溃，K 偏 −53% |

机制：屏幕锁定的准星标记与真实纹理**竞争相关峰**。纹理强时真实画面压得住，纹理弱时标记反客为主。所以：

- **「测一次没问题」不构成证据**。这是条件性故障，只在弱纹理下暴露，而实战中对着墙、阴影、雾天，纹理随时会弱。
- **patch 位置验证必须在弱纹理朝向下做**，好朝向会掩盖问题。
- 判别信号是 **std 而非 K 本身**：被标记污染的 patch 在 trial 间剧烈跳（std 0.777 vs 正常 0.006~0.027，差 25~130 倍）。

`calibrate_k.py` 的 per-patch 诊断已能自动区分两类故障：

| | 光学畸变 | 固定 UI 污染 |
|---|---|---|
| 各 patch std | 都小 | 某个极大 |
| K vs 距镜心距离 | 系统性单调 | 无规律 |
| 处置 | patch 向镜心收 | 把该 patch 挪开 |

顺带：这是 MAD 投票机制**第一次在真实场景救场**——坏 patch 偏了 53%，被其余 patch 投票踢出，最终 K 仍然正确（1.8757）。之前只在合成实验里验证过。

### 6.2 冗余：靠收紧 keepout 解决，不需要二维布局

原以为 4x 只能放 2 个 patch，要靠「镜内圆二维分布」才能补足冗余。实测表明**只要 keepout 按真实准星宽度收紧，中线上就能放下 5 个**，二维布局暂时用不上（留作 2x 这类小镜圈的备选）。

仍然备用的方案：

- **二维分布**：K 只从 1x 的 1.55 涨到 4x 的 1.88，说明倍镜焦距 f 大得多，而串扰 ∝ x·y/f²，所以镜内 patch 离开中线 300~400px 串扰仍在 0.5% 以内。2x 镜圈最小，若 3 个不够可用此法。
- **缩小 patch 到 96 或 64**：§3.2 证明小 patch 不会误匹配，代价只是量程（3P/8 = 36/24 px），而实测只用 12% 量程，撑得住。

配置固化在 `config.RECOIL_SIGHT_PROFILES`（K + patch_xs + keepout，按 sight 索引）。项目已有 `detector/attachment_detector.py` 可识别 scope 类型，运行时查表切换。

## 7. 游戏机制约束

### 7.1 Aim Punch 含纯视觉分量 ⚠️

PUBG 官方 Dev Letter 明确：aim punch 分两部分——
1. **aiming point movement**：准星实际位移（影响弹道）
2. **camera shake**：摄像机抖动，**不影响瞄准点**，且包含 **FOV 抖动**

FOV 抖动意味着 aim punch 期间 **K 是变化的**。这部分屏幕位移不该被补偿。

**处置：被击中的帧整段丢弃。** 检测：受击指示器 / 血量变化 / 位移严重偏离预测。

### 7.2 水平后坐力半随机

垂直是确定性上升，水平是 semi-random sway。**水平方向只能学系统性偏移，随机分量学不了也不该学**，否则是在拟合噪声。建议：
- 垂直：~~full per-bullet 残差学习~~ → ⚠ **按时间拟 `y_true(t)`，17 ms 网格**。「per-bullet」是弹桶坐标的说法
- 水平：只学全局偏置，或干脆不学

⚠ **上面那句「随机分量学不了也不该学」本身没变,而且它是这个仓库最贵的一课的另一种说法**:根 `CLAUDE.md` 记着一个 41 维模型去拟噪声,「改善」只存在于那一批测量上。

### 7.3 Recoil Recovery

停火后准星自动回落。**采集窗口必须严格卡在开火期间**——这条不变，而且它现在由「扳机按下到松开」这一段直接定义。

⚠ 原文后半句是「点射时每两次点射之间的 recovery 是污染源，需按 `bullet_interval` 切窗并丢弃间隔帧」。**没有 `bullet_interval` 这个东西了**：采的是连发整梭，`t` 从点击起算，而**非连发的梭在拟合器入口就被拒**（`calibration/fit_time_curve.py`，204 梭两侧标定过）。点射不是靠切窗处理的，是靠不收。

### 7.4 其他需确认

- 姿势（站/蹲/趴）对后坐力的乘子——项目已有 `posture_scales.json`，可作先验
- 配件减益是否严格乘法——决定 §分层模型能否用乘法分解
- 首发倍率（first shot multiplier）

## 8. 可追溯性：匹配必须留根

§5.2 的结论是「多个 patch 一致地错时自动检测会失效」。所以**不能把观测器当黑盒**——必须留下人能复查的证据，否则瞎匹配了也不知道，而且闭环学习会把错误自我强化。

与现有 `docs/mismatch/`（2026-08-08 前叫 `InGameScreenshot/`） 的收集模式保持一致。

### 8.1 三级留存策略

| 级别 | 存什么 | 何时 | 体积 |
|---|---|---|---|
| **L1 全量** | 位移序列、per-patch 值、player_input、comp、gate/MAD、时间戳 → JSONL | 每个弹匣 | ~20 KB |
| **L2 异常** | 触发帧前后的 patch 图像对 → PNG | 见触发条件 | ~50 KB/次 |
| **L3 抽样** | 完整 patch 序列（可回放重算） | 1% 弹匣 + 手动标记 | ~10 MB/次 |

L1 可以永久全存，L3 才是大头但只抽样。

### 8.2 L2 触发条件

按 §5.2 实测的检出能力排序：

| 触发条件 | 能抓什么 | 实测有效性 |
|---|---|---|
| **累积轨迹偏离预测 > Nσ** | 全体一致错（F3） | 唯一能抓 F3 的自动信号 |
| **sign-flip 特征**（方向与预测相反且幅度 ≈ P/2） | 量程超限（F2） | ✅ |
| **MAD 超阈值 / 有 patch 被剔除** | 少数派故障（F1） | ✅ 但对 F3 完全无效 |
| 时间域二阶差分异常 | 不物理的突变 | 待验证 |
| 梯度能量 gate 拒绝 | 纯黑/纯白病态帧 | ✅ |
| 弹匣内丢弃帧比例 > 20% | 综合劣化 | — |

⚠️ **不要只依赖 MAD**。F3 场景下 MAD = 0.016，比干净帧还小。

### 8.3 诊断图（人工复查的主产物）

人能快速判断的不是单帧位移对不对，而是**整条曲线合不合理**。每个可疑弹匣生成一张四联图：

1. 7 条 per-patch 逐帧位移曲线 —— 被剔除的点要**换色标出**，否则坏 patch 在细线里看不见
2. MAD + 每帧被剔除 patch 数
3. **累积位移 vs 预测** —— 最重要的一栏，F3 那种全体一致错只在这里可见
4. 残差 e 与子弹窗口切分

样例产物：`temp_debug/audit_magazine.png`（图）+ `audit_magazine.jsonl`（**66.6 KB/弹匣**，比预估的 20 KB 大，可通过降精度或只存 median+MAD 压到 ~15 KB）⚠ **两个产物和生成它们的脚本都不在盘上了**，那两个体积数是它们留下的全部。

### 8.4 回放与交叉验证

L3 存的 patch 序列可离线重跑，用途：
- 换参数（patch 尺寸、预测偏移策略）对比
- **用 RoMa v2 复算作为参考标准**，判断 phase correlation 是不是真的错了（§RoMa 的正当用途）
- 积累人工标注的困难样本集

### 8.5 曲线更新的闸门

⚠ **这四条全部预设「一次更新」这个单位,而那个单位没有了。** 拟合吃全库、一次出一条曲线,所以没有 diff 可记、没有单次幅度可限、没有「N 次更新之前」可回。原文留在下面当记录:

- ~~每次更新记录 diff（老曲线 vs 新曲线 vs 本次残差），可回滚~~
- ~~单次更新幅度上限（如 ≤5%），防止单个坏弹匣带偏~~
- ~~**早期 shadow mode**：只记录不生效，人工确认曲线走向合理后再开自动更新~~
- ~~更新历史留存，支持「回到 N 次更新之前」~~

**但第二条那个担心（一个坏弹匣带偏）是真的,而且它换了个更强的形状**:

> **离群的单位是一整梭,不是一个点。** 全文在 [`MODEL.md`](../MODEL.md)——它是主法则,这里只指过去。

⚠ **而「幅度上限」这类闸挡不住它**:一个坏梭的曲线形状正常,幅度也在范围内。⚠ 聚类也不是万能——一个只值 5% 的差异会直接并进邻居簇,`calibration/CLAUDE.md` 记着一次 5 对 5 的等量分裂,「取最大簇」在那种情况下等于掷硬币。

**样本永不删除**,被拒的梭改名留档而不是丢掉——那正是这一节「可回滚」想要的东西,只是落在数据上而不是落在曲线上。

## 9. 待验证项（按优先级）

| # | 项目 | 方法 | 阻塞什么 |
|---|---|---|---|
| 1 | **真实帧间精度** | 录连续帧，注入已知 counts，对比测量值 | 整个方案成立与否 |
| 2 | **K 标定** | 训练场 `pico.move()` 注入已知量反解，每种镜一次 | 单位换算 |
| 3 | **4x 可用区域** | 切 4x ADS 截图，扫中线带梯度能量与虚化边界 | §6 方案选型 |
| 4 | 端到端延迟 | Pico 遥测时间戳 vs 画面响应 | ~~`RECOIL_LEAD_FRAC` 辨识~~ → ✅ **已答**：`M ≈ 20 ms`，三个独立来源；`D = −19 ms` |
| 5 | RoMa v2 交叉验证 | 离线跑一批真实帧作参考标准 | 提高对 #1 的置信度 |

**#1 是关键门**：所有实测都基于「同一帧内整数行平移」，没有帧间光照变化、粒子、动画和亚像素重采样。这是**乐观上界**，真实帧间精度必须单独验证，不过关就不要往学习层走。

> ✅ **#1 已经答了，而且答案比这里预期的复杂**：相关器的逐对偏差 `b(δ)` **是那一对自己位移的函数,而且会变号**——δ≈0.6 px 时 +0.047 px/对(亚像素峰锁)，δ≈7–8 px 时 −0.21(帧内运动模糊)，**δ≈3 px 穿零**。一梭的 δ 分布横跨零点、正负对消，全库 272 梭代入净值 **−0.28% / −0.81%**。所以「固定 px」和「固定比例」两个模型都被否掉了(χ²/dof > 390，两个 run)。规格在 `MODEL.md` 3.1。
>
> ⚠ **而尺子的贡献只占逐梭散布的 ≤0.5%**（枪自己的逐发随机是 CV 2–4%）——**把相关器做得更准一分钱买不到，唯一的杠杆是多打几梭**。这跟这一节把 #1 排成「关键门」的判断不冲突：它当年确实是门，只是过了之后就不再是瓶颈。

## 9. 当前推荐配置

⚠ **这一节是当年的建议值。落地的形状在 `config.py`，两处不同，两处都在上面解释过：**

RECOIL_PATCH    = 128        # 宽，§3.4 的 gain 梯度定的
RECOIL_PATCH_H  = 256        # 高，§3.1 的量程定的 —— 建议值是 128
RECOIL_BAND_Y   = SCREEN_H // 2 - RECOIL_PATCH_H // 2      # = 592，仍以 720 居中

**七个 x 一个字没改**，所以 §2 和 §4 的结论是原样落地的；改的只有那一个高度。当年的建议：

# config.py — HUD_REGIONS 追加（y, x, h, w）  ← 历史，见上
'recoil_1': (656,  980, 128, 128),
