# 游戏机制备忘

自动化踩到的隐性机制。这些查不到——wiki 不写，社区帖子的版本对不上本机 build——只能实测或口述得来，所以踩一条记一条。

**记录格式**：触发 → 副作用 → 怎么检测 → 补偿动作。「怎么检测」这栏最重要：能检测的机制就不必预先知道，做完验证一下即可；只有检测不了的才必须靠这份文档预先规避。

**置信度**：`口述` = 用户告知未复现；`实测` = 脚本跑出来的；`推测` = 从别处推的，用前必须验证。

## 切换武器会退出开镜

| | |
|---|---|
| 触发 | 切换武器（按 1/2） |
| 副作用 | ADS 状态丢失，回到腰射 |
| 怎么检测 | 姿势图标在不在（见下条）——图标只在开镜时渲染 |
| 补偿 | 切枪后重新按右键开镜，且要等开镜动画走完再开火 |
| 置信度 | 口述（2026-08-01） |

影响：任何「换枪 → 开火」的自动流程都必须在中间补一次开镜。后坐力标定尤其敏感，`config.RECOIL_SIGHT_PROFILES` 对开镜/腰射用的是不同 K 值，状态错了整轮数据都是废的。

弹匣打空后游戏**自动换弹，且换完停在腰射**，所以每个弹匣之间都要补一次开镜（实测 2026-08-01）。

## 姿势图标只在开镜时渲染

| | |
|---|---|
| 触发 | 腰射（未开镜）状态 |
| 副作用 | HUD 的姿势图标整个不画，`PostureDetector` 返回 `None` |
| 怎么检测 | 就是它自己——图标在 = 开镜，图标不在 = 腰射 |
| 补偿 | 验姿势前先确保开镜；`Rig.ensure_ads()` 用图标有无来判断要不要按右键 |
| 置信度 | **实测（2026-08-05）**，见下表。原为口述（2026-08-01） |

**2026-08-05 量化了，而且比口述更绝对**（`tools/probe_posture_trace.py`，m416 在手，六个随机视角，4834 样本，`docs/posture/traces/20260805_094215`）：

| | 可读 |
|---|---|
| 开镜状态，任意时刻 | **3786 / 3787** |
| **不开镜**，整整 2000 ms 窗口 | **0 / 3787**，六轮无一例外 |

不是「有时候不画」，是**一帧都不画**。附带量到了另一个数：开镜状态下按姿势键，图标 **34–68 ms** 就跟上——所以任何「按了姿势键等一会儿再读」的延迟都不是瓶颈，**开没开镜才是**。`config.py` 三条触发因此改成读不到就重试（`retry_ms`/`retries`），而不是加大延迟；细节在 `detector/CLAUDE.md`。

⚠ **别用「准星缺席」去证明开镜**：空手时也没有准星，`AdsDetector` 会对着一个从没开过镜的角色返回 `True`。要证明枪在手上用**在场**证据——弹药数（`control.stock.weapon_in_hand()`）。

两个后果，方向相反：

- **坏的**：`ensure_posture()` 在腰射下读到 `None`，旧代码会落进 `else` 分支盲按 C。状态未知时按切换键，等于把角色扔进随机姿势，而且日志上只留一句 "could not reach posture"。现在读到 `None` 直接失败并 dump 截图。
- **好的**：右键是 toggle，盲按会切反，而 HUD 上没有别的开镜指示。图标有无正好补上这个读数，`ensure_ads()` 因此是幂等的。

顺序约束：Tab 会退出开镜，所以每一格必须按 **读配件（Tab） → 开镜 → 验姿势 → 开火** 走，不能把验姿势排在最前面。

## 换弹期间游戏不接受右键（约 2.0–2.3 s）

| | |
|---|---|
| 触发 | 打空弹匣，PUBG 自动换弹 |
| 副作用 | **换弹动画期间右键被吞**，`ensure_ads` 三次点击全落在里面 |
| 怎么检测 | 实测（2026-08-05，m416 ×4 弹匣）|
| 补偿 | **先 `wait_reload()` 等重装完，再点**。加长等待没用 |
| 置信度 | 实测 |

按「弹药数停止下降」起算，在固定时刻点右键：

| 点击时刻 | 生效 |
|---|---|
| 300 / 1400 / 1700 / 2000 ms | **0/4** |
| 2300 ms | 3/4 |
| 2400 / 4000 ms | **4/4** |

**而一旦生效，开镜只要 102–104 ms**——对着 `ADS_WATCH_S = 2.5 s`。所以那个 watch **从来不短**，它在等一个没人成功请求过的状态变化。而右键是 toggle，落在窗口外的那些点击会**两两抵消**，正是 `ensure_ads` docstring 里警告的自毁循环。

⚠ 判据不能是「点击后准星分数变了没有」——**换弹动画本身每帧让它动 +7**（60.8 → 111.2，前 187 ms，无输入）。要用 toggle 的算术：四次点击全生效必然交替，实测 `False,False,True,False`。

## 开镜后图标要 ~0.85 s 才出现

| | |
|---|---|
| 触发 | 按右键开镜 |
| 副作用 | 开镜动画期间姿势图标还没画出来，读到 `None` |
| 怎么检测 | 实测：静止时点击后 0.5–0.83 s 窗口内读 4 次全空，0.9 s 读到，轮廓面积 1000+ |
| 补偿 | 点击后**盯到出现为止**（`ADS_WATCH_S=2.5`），不要定时采样 |
| 置信度 | 实测（2026-08-01，`temp_debug/diag_ads_cycle.py`） |

这条本身不致命，致命的是它和「右键是 toggle」组合出的**自毁循环**：读不到 → 以为没开镜 → 再点一次右键 → 把刚开好的镜关掉 → 再读还是读不到 → 永远不收敛。表现是玩家看到镜反复切但状态毫无进展。

刚打完弹匣时更慢（连打 5 梭后必失败，只打 2 梭时能侥幸通过），所以窗口要按最坏情况给。

同类风险：任何「按键 → 立刻读 HUD 确认」的逻辑都要用「盯到变化」而不是「等固定时间再读一次」。

## 准星只在未开镜时渲染（比姿势图标更快更准）

| | |
|---|---|
| 触发 | 未开镜（腰射或肩瞄） |
| 副作用 | 屏幕中心画准星；一旦开镜，中心什么都不画 |
| 怎么检测 | `detector/ads_detector.py`，0.32 ms/帧 |
| 补偿 | 不需要——它就是读数本身 |
| 置信度 | 实测（2026-08-02，492 帧带标签，`calibration/fit_ads_detector.py`） |

**腰射和肩瞄的准星形状不同**：站定时四个刻度在 ±56 px，按住右键瞄准时会收紧。只匹配宽的那个，肩瞄会被读成开镜——`docs/ads/runs/20260801_222936` 整整 64 帧就是这么错的。两套模板都试、取较高分。

判据是「五个部件（四刻度 + 中心点）里最弱的那个」，不是「中心亮不亮」。要求四臂全亮才能排除镜子自己的准心——镜子只点亮中心：3x 上这一项把最差情况从 53.9 压到 0.03。而且必须用**相对量**（部件均值减环形背景），绝对亮度版本直接失效：开镜后画面被放大、边缘更锐，亮点数能到 3667，未开镜的反而可能是 0。

与姿势图标的实测对比（同一批数据，全程未开火）：

| | 准星判据 | 姿势图标 |
|---|---|---|
| 未开镜 | 0 错 / 344 帧 | 0 错 |
| 已开镜 @700ms | 0 错 / 148 帧 | **漏 5%** |
| 延迟 | 40–150 ms 之间 | 本批 150 ms 即出现 |

所以上一条记的 **0.85 s 是开火后的最坏情况，不是通例**——静止空载时图标 150 ms 就画出来了。两条方向相反（图标在 = 开镜，准星在 = 未开镜），可以组合成「确信开镜 / 确信没开 / 存疑」三态。

## 刷新器面板是全局的，逗号即开

| | |
|---|---|
| 触发 | 在训练场里按逗号 |
| 副作用 | 面板打开——**与人站在哪儿无关**，不需要走到刷新器旁边，也不需要面朝它 |
| 怎么检测 | `detector/spawner_detector.py`（右下三个按钮字形）。驱动是 `control.spawner.ensure_panel()` |
| 补偿 | 不需要 |
| 置信度 | 口述（2026-08-02，用户明确纠正） |

**自动化脚本不要写「请先站到刷新器旁」这类前置条件**，唯一的前置是游戏在前台。`harvest.py` 那句 `>>> Stand at an item spawner, facing something with texture.` 只有后半句成立：后坐力观测需要背景有纹理，位置本身无所谓。

## 物品刷新器的落位规则

| | |
|---|---|
| 触发 | 在物品刷新器里点一把枪 |
| 副作用 | 武器栏空 → 进 1 格；武器栏满 → 进 2 格并把原来那把**顶到地上** |
| 怎么检测 | 关掉面板后读 HUD 武器栏（面板开着时武器栏被遮住） |
| 补偿 | **点一次**。武器栏在实际流程里从来不空，所以第一次点击就落 2 格 |
| 置信度 | 口述（2026-08-01 落位规则，2026-08-02 点一次） |

一度改成「同一把枪点两次」，理由是空/满/半满三种起始状态都收敛到 2 格——收敛是收敛了，代价是**每刷一把枪就往地上扔一把**：满栏是常态，第二次点击顶掉的正是第一次刚放进去的那把。收敛性本来就是推导，不是实测。

「怎么保证枪在 2 格」是**调用方的策略，不是 `SpawnerControl` 的默认**。`give_weapon` / `give_many` 一次点击刷一把，要更强的保证就自己读武器栏，或者显式传 `times=2` / `weapon_times=2` 买那个收敛（并接受地上多一把）。

配件点了进背包，面板右上 `物品 N/200` 就是背包计数，可以直接当溢出监控读。

## 没有背包，配件就没地方去

| | |
|---|---|
| 触发 | 刷新器刷配件，而角色身上没有背包 |
| 副作用 | **不会报错**。配件不知去向，库存行位错乱，之后每一次拖拽都落在错的格子上，装配读回的是没人要的东西 |
| 怎么检测 | 事后才看得见：`muzzle should be comp_ar, reads 'Muzzle_Suppressor_Large_C'`，然后连续 7 个配置全部 `could not reach config` |
| 补偿 | **开跑第一件事刷三级包**（`control/spawner.py` 的 `GEAR['backpack3']`，col3_row06 第 3 项），再刷配件。重进训练场后要重来一遍 |
| 置信度 | 实测 + 口述（2026-08-02，用户指出） |

刷新器第 3 列此前完全没建模（只有武器列和配件列）。这一列是 汽油桶 / 能量物品 / 治疗物品 / 头盔 / 防弹衣 / 背包。

## 刷新器菜单：每列各留一个展开，跨列互不影响

实测 2026-08-03（22 次真实转移，从 `goto()` 每次追加的那份 path log 里读的）。⚠ **读它的那个脚本 2026-08-08 删了**：它挂着 pixi task、每次都跑，而 `main()` 无条件 `return 0`——**构造上不可能红**。那天把 30 个闸逐个做变异测试，只有它一个是「绿得没有能力变红」。分桶函数 `classify` 是真的，搬进了唯一钉它的地方（`tools/test_spawner_plan.py`）。**代价说清楚：现在没有任何东西在看那份 live log 了**——在此之前也没有，只是当时看起来有。原来的问题问错了——不是「手风琴还是多开」，两个都不对：

**面板每列保持一个展开的类别，而且跨列各自独立。** 展开 col2_row01 **不会**关掉 col1_row01，两列同时开着。所以代价取决于**方向**，不取决于任何手风琴规则：

| 转移 | 击数 | 为什么 |
|---|---|---|
| 目标**已经开着** | **0** | 多开的红利：在另一列干活时这一列保持展开 |
| 同列**向上**（目标在已开的上方） | **1** | 没东西挡路 |
| 跨列 | 1（首次），之后 0 | 各列独立 |
| 同列**向下**（目标在已开的下方） | **2–3** | 已展开的子菜单把目标行往下推约 360 px，坐标落到别处，必须先关它 |

**推论**：批量刷东西时，同一列内**从下往上**走比从上往下走便宜。

`plan()` **已经这么排了**（`items.sort(key=... -s['category'][1] ...)`）。值得记的是这条规则被**两条独立路径**推出来过：一条从几何——展开的子菜单把下面的行推走，实测 `live_two_open.png` 里 MAGAZINE 从 y=349 掉到 y=709，坐标会落到子菜单条目上、**点出一个没人要的东西**；另一条从点击代价——同列向下 2–3 击、向上 1 击。同一条约束，一个说「会点错」，一个说「会更贵」。

### 顺带查出的 bug（已修）

`PanelState.expanded` 只能装**一个** `(col,row)`，而 `expansions()` 返回列表，`_read()` 取 `found[0]`（列序）。于是只要 col1 开着，`at(2,1)` 永远是 False——`goto()` 以为自己那一击失败了，collapse 全部再点一次。

实测代价：**进 col2 恒定 2 击、8/8，反方向 1 击、8/8**。那个不对称跟菜单毫无关系，是一行代码把列表塞进了单个槽位。

那句注释写着「42 帧真值里从没见过两个同时展开」——**因为那 42 帧全部从折叠态展开**，这个状态它们一次都拍不到。

修法：`PanelState.all` 装全部，`at()` 查成员，`entries_for(col,row)` 按节点取条目。最后一条同样要紧：`spawn()` 的条目数守卫原来用 `st.entries`，两列开着时会拿 col1 的条目数去对 col2 的期望。

## 刷新器不知道你已经有什么，点一次就多一件

| | |
|---|---|
| 触发 | 每次进场／重进场都无条件把整份配件清单刷一遍 |
| 副作用 | 背包越堆越满（同一个补偿器三四个），最后新刷的配件没地方落；更麻烦的是 `TabView.find()` 会挑到"另一个"同名件，而行号随增删漂移，拖拽落点不稳定 |
| 怎么检测 | 开 Tab 读 `库存` 行，同一个 catalog key 出现 >1 次 |
| 补偿 | 先看后刷：`control/stock.py` `restock()` —— 读背包 → 缺背包先刷背包 → 多余的丢地上 → 只刷差的那几件。已在枪上的件算"有"，无模板的行（弹药/药品）一律不动 |
| 置信度 | 实测 + 口述（2026-08-02，用户指出） |

背包穿没穿，直接看角色装备格 `EQUIP_SLOTS['backpack']` 的 Laplacian 方差：穿了约 2900（画了图标），没穿约 44（透出模糊背景）。只能判有无，判不了等级——1 级包和 3 级包一样都是"有"。

## 挂机会被踢下线，弹窗挡住一切

| | |
|---|---|
| 触发 | 静置若干分钟。**不只是大厅——站在训练场里不动同样会被踢**（2026-08-06 实测） |
| 副作用 | `错误 / 因长时间没有动作, 您已被踢出游戏。`，模态弹窗，**挡住重进流程**——无人值守跑一旦踩到就再也自己起不来 |
| 怎么检测 | `error_dialog_visible()`，匹配 `ERROR` 标题字形 |
| 补偿 | `dismiss_error()` 点 OK `(1709, 904)`，在 `ensure_in_match` 和 `exit_to_lobby` 里都排在最前面 |
| 置信度 | 实测（2026-08-02 大厅 `docs/lobby/error_inactivity.png`；2026-08-06 训练场内 `docs/lobby/error_dialog_0806.png`） |

⚠ **「静置」的时钟不是游戏在跑的时候，是 agent 在想的时候。** 2026-08-06 一晚上踢了五次，每一次的前一个空档都是我在写分析、改代码、不驱动游戏。采集本身一直在开枪、开关 Tab、点刷新器，**一次都没被踢过**。

**窗口实测 ≤ 8 分钟**（上界，没测下界）：

| 上一轮结束 | 下一轮开始 | 空档 | 结果 |
|---|---|---|---|
| 14:33:36 | 14:49 | 15 min | 被踢 |
| 15:05 | 15:13 | **8 min** | 也被踢 |

**所以规矩是：先把下一轮发出去，再去分析。** 一次重进要 20–29 s，还得重新备货、重刷枪。

⚠ **这个弹窗一上，症状会伪装成刷新器和检测器的故障**，而且每一条消息本身都是真的：

```
[stock] spawned 1 in 2 clicks: vss        ← 点击发出去了，打在模态上
[!] vss is not in the rack, and both slots are empty — the spawn did not land.
[!] posture unreadable (want standing)    ← 没有 HUD 可读
```

**弹窗上写着原因，而没有一段代码去读它。** 现在 `harvest_weapon` 的取枪失败会先问 `session.in_range()`，分得开「刷新器没给」和「人已经不在局里了」，后者重进 + 重新备货再试一次（`SETUP_TRIES`）。以前 `session.ensure()` 只在**两把枪之间**调，所以 `--weapons vss` 这种单枪轮（也就是每一次收敛验证）**一次驱逐就整轮报废**。

⚠ **未解释**：14:49 那轮重进成功（29 s），~30 秒后就死在同一个弹窗上。是被第二次踢了，还是重进本身没真正落地（`IN_GAME` 成立但角色还在加载），日志分不出来。**别把这一条当成「重进不可靠」的证据**，它现在只是一个没定的问题。

## 服务器会断开会话，断线界面伪装成大厅

| | |
|---|---|
| 触发 | 挂机下线之后（也可能自己发生） |
| 副作用 | `ERROR / The service is not available at the moment.` + **RECONNECT** 按钮。整个界面几乎全黑 |
| 怎么检测 | `LobbyState.DISCONNECTED`——判据是 RECONNECT 字形 |
| 补偿 | `click_reconnect()` 点 `(1730, 906)`；实测 `断线 → 加载 → 局内` 约 15 秒 |
| 置信度 | 实测（2026-08-02，截图 `docs/lobby/error_disconnected.png`） |

**这个必须是状态，不能只做成一个门控。** 画面全黑 → 信箱黑边亮度 0 → `classify()` 判成 `LOBBY` → 上层去点 PLAY → 毫无反应 → 白白耗掉 3 次重试和 30 秒。它和挂机弹窗是**两个不同界面**：那个是盖在大厅上的对话框、按钮是 OK；这个在断线页、按钮是 RECONNECT。两者的 `ERROR` 标题只差 38px，靠位置区分是在赌，所以判据用 RECONNECT 字形（它是唯一的）。

**`FULLBLEED` 现在有三种含义**：加载页、退出确认框、错误弹窗。三者处理方式两两不同（什么都别碰 / 点 CONFIRM / 点 OK），而像素判据分不开它们——错误弹窗的暗化遮罩把信箱黑边从 0 提到 60，正好越过 `LOBBY_BAR_MAX=8`。所以每一个都得有自己的字形门控，`tools/verify_lobby_detector.py` 里有互斥回归。

## 右键装配件 —— 装到「手持的那把枪」

| | |
|---|---|
| 触发 | Tab 界面里对库存/地面的一个配件**右键** |
| 副作用 | 它直接装到**当前手持**的枪上；不需要拖 |
| 怎么检测 | 装完读 `read_slots(gun)`。想指定装哪把，先切枪（按 1/2）再右键 |
| 补偿 | 无需补偿。要装到另一把枪就先按对应数字键 |
| 置信度 | 实测（2026-08-02，2×2 每格 5 次，读回验证）|

实测两组，各自把两把枪的槽位都清空后右键同一个配件：

| 手持 | 装到了 |
|---|---|
| 武器 1 | 枪 1 |
| 武器 2 | 枪 2 |

**右键比拖拽快 5 倍，而且拖拽这条路当场一次都没成功：**

| 手势 | 落位 | 中位耗时 |
|---|---|---|
| 右键 | **4/4** | **0.35s** |
| 拖拽（库存 → 枪口槽） | **0/4** | 1.70s |

拖拽失败与 `DROP_WAIT` 无关——把它调回原来的 0.25 s 一样是 0/3。所以「配件有时候装不上」不是时序问题。

⚠ **这条 0/4 跟「拖不到地上」不是同一件事，别混。** 这里验的是**槽位读回**（模板匹配枪上那个槽），而且**反方向的 `unequip` 同轮全中**——两条都说明判据在工作，0/4 是真的落不下去。而面板到面板的「拖到地上」曾经报出的 ~0.5，是**判据自己的产物**：光标偏出 2 px 就跳过读回，那类记录里 98% 东西已经落地了（2026-08-08 复核，`control/CLAUDE.md`）。**一个方向性的真失败，和一个不看物件的判据，报出来的都是「拖拽失败」。**

**而且是方向性的**：同一轮里 `unequip`（枪口槽 → 库存，往左拖）每次都成功，只有反方向（库存 → 枪口槽）落不下去。

| 方向 | 手势 | 结果 |
|---|---|---|
| 库存 → 枪 | 拖拽 | **0/4** |
| 库存 → 枪 | 右键 | **4/4**，0.35s |
| 枪 → 库存 | 拖拽 | 成功 |

所以：**装用右键，卸用拖拽**。右键表达不了的（丢地上）仍然走拖拽。

### 复测 2×2：手里拿不拿枪，没有区别（2026-08-03）

上面那组只变了一个变量——**两条路径都没有 `hold()`**。于是「拖拽 0/4」是在没拿枪的条件下测的，而
`control/CLAUDE.md` 又写着「右键只够得着手上那把枪」。两句话不可能同时成立：要么那条规则错，
要么拖拽从来没拿到过它需要的条件。旧表说不出是哪一个。

2×2，每格 5 次：

| 手势 | 手里拿枪 | 落位 | 中位耗时 |
|---|---|---|---|
| 右键 | 否 | **5/5** | 0.17s |
| 右键 | **是** | **5/5** | 0.17s |
| 拖拽 | 否 | **0/5** | 1.68s |
| 拖拽 | **是** | **0/5** | 1.68s |

两条结论：

1. **右键 10/10，不需要 hold。**「右键只够得着手上那把枪」这条**在单枪场景下不成立**——没拿枪照样进。
   机架里有两把枪时是否需要按 1/2 来指定目标，**没测过**，别当已知。
2. **拖拽 0/10，拿着枪也一样。** 不是没给够条件，这条边就是不通。

拖拽那半边跑的是 `equip(gesture='drag')` 强制的——`'auto'` 在拿着枪时会自己改用右键，
那样就会把右键测两遍然后当成拖拽的结果报出来。

## 整枪能直接扔地上，配件跟着走

| | |
|---|---|
| 触发 | 枪械行左端那个**方框数字**（`1`/`2`）——**右键点一下**，或者向左拖进「附近」列表松手 |
| 副作用 | 整把枪掉地上，**身上的配件全部跟着走**，一件都不回背包 |
| 怎么检测 | 读枪名牌：有 → 无。地面多一行；**注意那一行匹配不到任何配件模板**，`item.key` 是 `None`，数 key 会以为地上是空的（数 `view.rows('nearby')`）|
| 补偿 | 不需要。`InventoryControl.drop_weapon(gun)` 默认 `gesture='auto'`（先右键，不成再拖）|
| 置信度 | 实测（2026-08-02，右键 / 拖拽两种手势各跑一遍）|

**右键和拖拽都行，右键快一倍。** 同一把 aug 带 4 件，成对实测：

| 手势 | 落位 | 端到端 | 库存变化 | 地面变化 |
|---|---|---|---|---|
| **右键** | 1/1 | **0.66 s** | +0 | +1 行 |
| 拖拽 1621 px | 1/1 | 1.15 s | +0 | +1 行 |

两个数都含 `DROP_SETTLE` 的 0.5 s 和两次读帧，所以**手势本身**是约 0.16 s 对 0.65 s，差四倍。一轮 harvest 每把枪付一次，所以默认走右键。

（早先记的「1.16 s」是拖拽，跟这里的 1.15 s 一致。）

**这就是「换枪前先卸干净」的正确做法**——不要先 `strip()`。拆下来的配件会回到背包，而 PUBG 会把背包里装得上的**自动装到下一把枪上**，于是一轮标着 BARE 的数据带着 `Lower_Foregrip_C` 和快拉弹匣跑完了。整枪扔出去，下一对枪才是干净的，地面也不会污染下一轮。

目标点是**方框数字**，不是名字牌、也不是下面那排配件格：`(2237, 145)` / `(2237, 447)`，`detector/tab_layout.gun_tag_point`。右键和拖拽用的是同一个点。

## 右键点一个**空的**配件槽，会把整把枪扔地上

| | |
|---|---|
| 触发 | 对**没有东西**的配件槽发右键（卸配件用的那个手势） |
| 后果 | 点击穿到下面那一行武器上，等价于右键点枪械行 —— **整枪连配件掉地上**（上一节那条） |
| 怎么检测 | 枪名牌墨迹 `plate_ink` 从 679–901 掉到 **0**，武器面板整块不再绘制；地面多一行 |
| 怎么避免 | **点之前先确认槽里有东西**，而且不能用模板确认（要采模板的那些件本来就读不出来）。用 tile 几何：`SlotDetector` 的 `filled`（内部 Canny 202–885 vs 空槽 0–71） |
| 置信度 | 实测（2026-08-03，`calibration/collect_templates.py` 连续三轮 × 6 件，`facts.misses` 里 `step=take_off`） |

**它长得跟成功一模一样。** 右键卸配件在**槽里有东西**时是实测 3/3 进库存的，所以调用方拿到的是同一个手势、同一个返回；区别只有屏幕。三轮 18 次全部收零，日志每一行都正常：`gun_slot()` 说枪在 slot 1、`read_slots()` 说它穿着四个配件、`SlotDetector` 把面板后面模糊的地形读成 `empty`——**三个读数在一个没有枪的机架上各说各的**，只有名牌墨迹是 0。

推论，比这条本身更值钱：**先问「这一格里有没有枪」（`plate_ink`），再问「这个槽里有没有东西」。** 顺序反了，第二个问题的答案是拿风景算出来的。

## 拖放的落点，只在拖拽进行中才画出来

| | |
|---|---|
| 触发 | 把配件从枪上拖向 库存 / 附近，**释放点用行坐标算** |
| 副作用 | 槽位空了，但件掉在**地上**，不在背包里 |
| 怎么检测 | 只读源槽读不出来 —— `drag()` 就是只验源槽。要数**目的地**面板的行数，或比对物品多重集 |
| 补偿 | 用量出来的落点：`detector/tab_layout.DROP_XY`。或者直接右键（`unequip` 默认） |
| 置信度 | 实测（2026-08-02，干净复现两次）|

**放置区在静态截图里不存在。** 拖着东西不松手的时候，游戏才会给每个能接收的面板画一圈虚线框。量法：拖过去 → 停住别松 → 截图（`tools/snap_on_key.py` 按热键截并把光标坐标戳进文件名）→ 随便松手。两张图给出两个矩形和两个已知可用的释放点。

```
DROP_XY = {'inventory': (1128, 611), 'nearby': (744, 570)}
```

**把模板匹配的图标中心当释放点，是这个 bug 的具体形态**——`PANELS[panel][2]` 是给识别用的列中心，不是给放置用的。两个是关于同一个面板的两个不同问题。

这个错误活了几个月没人发现，因为 `drag()` 只重读**源槽**：槽位空了就算过。`strip()` 和 `ensure_kit` 的卸载兜底都走这条路。

⚠️ **边界没测出来**：到底哪个坐标开始从"进包"变成"掉地上"，没有结论。做隔离实验时两个列表都顶到了 12 行的显示上限，行数差在那种状态下没有意义，那批数据作废了。已确立的只有：这两个点可用，旧的行坐标不可用。

⚠️ **列表满了行数就不会涨**：库存和附近各显示 12 行。件确实进了包，行数还是 12，天真的「+1」判据会把成功读成失败。要比对**物品多重集**。

⚠️ **上面那个「边界没测出来」在 2026-08-04 有答案了，而且答案是「边界不存在」**：落点在 `附近` 面板里怎么放都行，见下一节。真正卡人的是**手势本身**，不是坐标。

## 拖拽有两个悬崖：每步跨多远、松手后停多久

| | |
|---|---|
| 触发 | 光标每次更新跨 >35 px，或松手后立刻移走 |
| 副作用 | 东西没到目的地，**而手势报成功**（面板到面板的拖拽没有槽位可读回） |
| 怎么检测 | 数目的地面板的行数，且**一次拖拽一次读回** |
| 补偿 | `press/pointer.py: DRAG_STEP_PX=32`（按距离算步数）、`control/inventory.py: DROP_WAIT=0.25` |
| 置信度 | 实测（2026-08-04，每次拖完立刻读回）|

```
每步位移   15px 3/3    21px 3/3    35px 3/3  |  52px 1/3    104px(一跳) 0/3
松手静止   0s 0/12     0.15s 2/3   0.20s 3/3 |  0.25s 21/21
```

**悬崖正好在人手的上限上。** 录了 34 次真人拖拽（`temp_debug/record_human_drag.py`，1 kHz 采光标）：每次位置更新中位 **18–25 px**、最大 **51**、间隔 7.7 ms。游戏能接受的上限 ~35 px，正是人手日常范围的顶端。

**旧代码的 `DRAG_STEPS = 10` 是固定步数**，所以 1600 px 的 库存→附近 每步 160 px，三倍于悬崖——**那条拖拽从来没有成功过**，只是没人把它和「刷不出枪」联系起来。

**松手后必须静止 0.25 s。** 这一条曾被优化掉，理由是「拖拽靠轮询验证，等待被 VERIFY_TIMEOUT 吸收」。漏掉的是唯一不轮询的那类：目标是**面板**的拖拽没有槽位可读，`drag()` 松手瞬间返回，下一个手势立刻把光标拽走。12 件配件清库存，`drop=0` 掉 0 个、`drop=0.25` 掉 12 个，而两种情况下每一次都打印 `dragged`。

代价在上游：清不空的库存会填满，而**满库存会让刷新器静默地什么都不出**（见「没有背包，配件就没地方去」）。三轮模板采集因此报废，日志里只有 `no bare host gun`。

**释放点只要越过两栏之间的虚线。** `附近` 到 x=880、`库存` 从 x=907 起，870 是第一列，从 库存 行 0 过去 104 px（`DROP_XY` 那个点是 437 px）。y 用抓取行的 y 即可，**不需要找空行**——往已有物品的行上放实测 5/5。

⚠️ **「往已占用的行上放会失败」是个错误结论，别再得出一次。** 它来自连续拖 3 次、最后统一读回的测法，稳定 2/3；那 1/3 失败是上面的 `DROP_WAIT`，跟落点无关。同样的落点逐次读回是 5/5 和 6/6。**测拖拽必须一次一验。**

| | |
|---|---|
| 触发 | 往一个**已占用**的配件槽装新配件 |
| 副作用 | 从**库存**装 → 旧配件回**库存**；从**地面**装 → 旧配件掉**地面** |

## 刷出来的配件去哪：空槽位自动上枪，否则进库存

每格 3 次，槽位占用状态用 `read_slots` **读出来**而不是推出来：

| 条件 | 结果 |
|---|---|
| 机架里没有枪 | **库存** 3/3 |
| 有枪、目标槽位**空** | **直接上枪** 3/3 |
| 有枪、目标槽位**已占用** | **库存** 3/3 |

配合已知的另一条（枪刷出来时会从背包捡装得上的），完整规则是：

> **配件和枪，谁后到谁去找对方；能装就装，装不下才进背包。**

### 这条被测错过一次，值得记

第一版探针用 `detail ≥ SLOT_DETAIL_MIN` 判「槽位空不空」，得出「有枪槽位空 → 进库存」。**那是假的**：
`SLOT_DETAIL_MIN` 答的是「这个格子里画了 UI 没有」，而枪一进机架，它拥有的槽位就全画出来了——
实测一个**空**枪口槽是 **728**，而阈值是 **100**。所以条件「槽位空」从来没成立过，
测的一直是「槽位有东西」那一格，答案自然是库存。

**用一个恒真的判据去建立实验条件，实验就没做过，而结果照样会打印出来。**

### 对采集的意义

`calibration/collect_templates.py` 靠这条规则**安排**落点，而不是绕开它：
同一个件刷两次——第一次槽位空、自动上枪，拍 `slots`；第二次槽位被它自己占着、进库存唯一一行，拍 `rows`。
两张图都是同一个件，身份由「只刷了这一个」保证，不问检测器也不依赖库存的排序。

**加长超时救不了**——按键根本没到，等再久也等不出来。这是它和「界面画得慢」的
本质区别，两者症状一样但解法相反。所以 `TAB_TOGGLE_TIMEOUT` 反而从 1.0 s 降到
0.5 s：单次等待要短，好把时间留给重按。

`sweep.ensure_inventory_open(tries=3)` 早就带着重试，现在知道那个 3 不是保险，
是必需的。

实测的开关耗时（`tools/probe_toggle_latency.py`，t=0 是 `key()` 调用，含 CDC
写入和固件报文）：

| | 打开 | 关闭 |
|---|---|---|
| Tab 背包 | 28–38 ms | 77–128 ms |
| 刷新器面板 | 32–44 ms | 202–232 ms |

Tab 的「出现」和「画完」在 8 轮里**完全相同**——两把枪那块面板不是渐进绘制的，
认出锚点就可以直接读。刷新器的类别列不是这样，见 `SpawnerControl._recalibrate`。

## 关掉 Tab 之后，面板还能再截 20 毫秒

| | |
|---|---|
| 触发 | 按下关闭 Tab 的键之后立刻截图 |
| 现象 | 面板**完整可读**，能连截 3–4 张；最后一张有效的在 13–28 ms |
| 怎么检测 | 存下每帧再离线判读，见 `docs/tab/close_race/` |
| 置信度 | 实测（2026-08-02），3 轮 |

**没有淡出动画**：面板不是渐隐的，是在相邻两帧之间整块消失。所以一张截图要么
拿到全部、要么什么都没有，不存在画了一半的中间态——前提是抓得够小够快。全屏
70 ms 的 BitBlt 跨过这个切点，就没有这个保证了。

所以「为了拿到最后状态而先关再开」是不必要的：**关之前直接抓就行**，甚至关了
之后还有 20 ms 的余量。真正省事的地方在于根本不用翻转——`tab_open()` 只要
3–6 ms，状态问一下就知道，不用自己造一个已知状态出来。

## 两个「扩容弹匣」容量不一样：`ext_ar` 42 发，`quickext_ar` 40 发

| | |
|---|---|
| 触发 | 给同一把 m416 装 `Magazine_Extended_Large_C` 或 `Magazine_ExtendedQuickDraw_Large_C` |
| 现象 | 前者弹匣读 **42**，后者读 **40** |
| 置信度 | 实测，**57 次 vs 9 次**，各自零例外（全仓 `docs/recoil/runs/` 统计，2026-08-07） |

名字读起来像「同一个东西，一个抽得快」，容量却差两发。⚠ **快拉那个是更小的**，跟直觉相反。

**为什么这两发要命。** 后坐力曲线是按弹匣长度拟合的，而固件从点击那一刻起**按自己的时钟把整条曲线播完**——弹匣里没有的那两发照样发补偿，把准星往下压而没有后坐力可抵消。所以拿 42 发的曲线打一个 40 发的弹匣，测出来的不是后坐力，是这个错配。

实测代价（m416 bare，2026-08-07）：

```
八轮 ext_ar（42 发）    残差 −1%          真实后坐力 1450–1590
一轮 40 发             残差 −39%          真实后坐力 713
```

而 `--apply` 照单全收，把存着的曲线从 3248 counts 推到 2712，并且**从 42 发截成 40 发**——每一次写入看起来都跟平常一样。随后一梭 shadow（刚刷出来的干净 `ext_ar`）读回 42 发、1500 counts，**证明曲线一直是对的，异常的是弹匣**。

⚠ **槽位读回说不出这件事。** 那一轮的读回是 `ext_ar`，而弹匣只有 40 发——两个扩容弹匣的图标模板足够像。**能分开它们的是弹匣长度本身，不是模板。**

拒绝这件事的代码搬过家：`fit_curve.rebuild()` 已删，现在是 `calibration/collect_timed.py` 的 `prior` 检查（`mag_size not in prior`），**在开火之前**问「这一梭的容量和这把枪存过的每一梭一样吗」。

⚠ **它 2026-08-09 从「拒绝」降成「报告并入库」**，因为上面那段引用的代价属于**旧坐标**：曲线按弹匣长度拟合，短两发就多播两发补偿。时间坐标下不存在这件事——`y_true(t)` 在重叠窗口里是同一条曲线，长的那梭只是尾巴更长，而每个因子现在都在**共同的 t** 上读。⚠ 而**拒绝让「弹匣这个件本身动不动后坐力」永远问不出来**：要回答它的那些梭正是被拒掉的那些。

## mg3 有**两档射速**，而记录里只有一个数

| | |
|---|---|
| 触发 | 打 mg3。射速档由火力模式键切换 |
| 现象 | 同一把枪、同一个动作，逐发间隔要么 ~60 ms 要么 ~90 ms |
| 怎么检测 | **打完读弹药计数器**。剩下的发数 > 0 就是这一梭没打完 |
| 补偿 | `hold = 剩余发数推出的真实间隔 × 发数`，见下 |
| 置信度 | 实测两次，**两次都不知道自己在测哪一档** |

```
2026-08-04   59.97 ms（1000.5 rpm）   3 梭，弹孔检测，残差 0.06 ms
2026-08-09   88–92 ms（652–682 rpm）  6 梭，弹道自相关，另有 2 梭落在二次谐波
             比值 1.50
```

**两个数都是干净的测量，而它们描述的是这把枪的两个不同状态。** 1.50 这个比值和社区说的 990 / 660 对得上。

⚠ **而「火力模式」在这个仓库里从来不是猜的,只是没人调用它:**

| 早就存在的东西 | 状态 |
|---|---|
| `FireModeDetector` 能吐 `high` 这个标签 | 训练语料 859 张,`high` 是其中一类 |
| `GunDriver.ensure_fire_mode` 按 B 并盯着 HUD 直到读到目标 | 写好了 |
| `FIRE_MODE_FOR = {'mg3': 'high'}`,注释写着「MG3 有两个自动档,慢的和快的」 | 写好了 |
| **采集路径调用它** | **一次都没有** |

**所以这不是「游戏藏了一个机制」,是「本仓库知道这个机制、能读它、能切它,然后每一梭都没问」。** 两次测量各自打在枪碰巧刷出来的那一档上,而没有任何一梭记下自己是哪一档。

2026-08-09 起 `Magazine.fire_mode` 存读回,`samples.fire_tag` 用它决定**这一梭进哪个文件**——枪的常规档不带标签(mg3 是 `high`,别的枪是 `full`),故意测另一档的进 `__fire-<mode>`,两档永不混池。⚠ **存量的 12 梭 `mg3__bare.jsonl` 因此是可疑的**:它们的轨迹自证 ~90 ms(= `full`),却躺在 `high` 的文件名下,而且每一梭长度都不同。要用它们之前先按 `.MISLABELLED_` 隔离。

### 它是怎么烧掉一整格的

按 60 ms 给 75 发排的扳机只按 4.53 s，而真实需要 6.7 s，于是每梭**剩约 25 发在枪里**。接着换弹从半带开始、`wait_reload` 等不到 75 发超时，下一梭的计数器读到的是一个**半满的带子**：

```
75 → 25 → 58 → 36 → 50 → 41 → 47 → 43 → 46 → 44        每一梭长度都不同
```

每一梭本身都是自洽的（读多少发就打多久），所以**没有任何一条报文说这里不对**——直到臂检验报 12.6% 不一致，而那句话指向的是「拟合」，不是「扳机」。

⚠ **修法不是把 mg3 的常数改对。** 常数只有一个而枪有两档，改了下次切档照错。改的是**打完问一句计数器**（`Magazine.rounds_left`）：剩了就说明按短了，用 `hold ÷ 实际打出的发数` 当下一梭的间隔。这对每把枪都成立，而且不需要知道 mg3 有两档这件事。

## 开一次 Tab 就会掉出 ADS

| | |
|---|---|
| 触发 | 开镜状态下打开 Tab（读挂件、读枪名、盘库存，任何一种） |
| 现象 | 关掉 Tab 回到世界时人已经在**腰射**，而且没有任何提示 |
| 置信度 | 实测（2026-08-03，`auto_calibrate` 迁移时撞出来） |

跟 552 行那条「换弹也会掉出 ADS」是同一类，**但触发点完全不同**，两条要分开记：
换弹是角色动作，读 Tab 是界面动作，而一个只读界面的动作会改变角色状态这件事
没有任何直觉能提示。

**它污染数据的方式是结构性的，不是偶发的。** `auto_calibrate` 原来只在 `i > 0`
时开镜，第一个弹匣靠人。而挂件检测每轮开局都要读一次 Tab——**所以只要开着挂件
检测，mag 0 必然腰射**，然后拿开镜的 K=1.55 去分析 K=0.50 的运动，**读高约三倍**。
这不是「偶尔有一梭坏了」，是每一轮的第一梭都坏，而且每一轮都坏得一模一样，
所以看起来像一个稳定的系统性偏差而不像一个 bug。

**推论，对所有测量脚本成立**：任何读 Tab 的动作都必须排在 `ensure_ads()`
**之前**；开火前重新确认一次，别相信开火之前某个时刻确认过的结果。

## 客户端会掉线，而它污染数据的方式不是「跑不动」

2026-08-06 一晚断线 **三次**，弹出的是中文错误框「错误 / Connection to lobby ended / 重新连接」——**即使客户端其余部分是英文**。

**代价不是那三次失败的运行，是断线之前那一轮。** 11:02 的 vss 格残差是 `+348 / −61 / −108 / +196 / +346`，离散 ±195，而同一把枪同样设置前后两轮是 **±28.9 和 ±9.6**。当时花了很久怀疑是当天改的四样东西（末发规则、瞄准比例、`top_up`、换弹 settle），逐个排掉之后才发现**那一轮正是断线前最后一轮**。

机制：**连接要掉之前会先卡顿**——画面停住，然后一帧追上来。**那一跳在这套测量里和「被车撞」完全一样**，都是单帧巨大位移。当时那个常数叫 `FRAME_JOLT_PX`，按**症状**命名而不是按原因，因为两种来源它分不开，也不需要分开。

⚠ **那个常数和它所在的 `calibration/analysis.py` 已随旧坐标删除。** 接手同一件事的是 `detector/view_tracker.py` 的 `out_of_range`——判据从「位移超过某个像素数」换成了「读数离预测太远」，判据在那个文件里，这里不复述。

⚠ **所以看到 `hit the character` 大量出现时，先看是不是网络**，而不是数今天训练场有几辆车。

### `LobbyControl` 认识那个对话框，卡住的是下一步

三次失败报的都是 `states: ['error', 'lobby']` + `ensure_in_match: 3 attempts had no effect, stuck in lobby`。**读法要准**：`error → lobby` 那一跳成功了（它会自己点「重新连接」，坐标实测 (1709, 904)，金色按钮框 (1573,855) 293×73）。**失败的是紧接着的 `lobby → in_game`**——重连之后立刻点 PLAY，客户端还没准备好。

同一份 `LobbyControl` 在别的时候能一路走通（`error → lobby → fullbleed → in_game`，13.4 s），所以不是不认识，是**没等**。

**待修**：`error → lobby` 之后加一个等待再点 PLAY。今晚为此手动点过两次重连——**那两次其实是多余的**，它自己会点。
